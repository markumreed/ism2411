Index Practice

Teaching goal: zero-based positive indexing, negative indexing from the end, and computing a "middle" position from len() rather than hardcoding it — the single most important non-obvious idea in this lab. Say to the class (verbatim): "This is the idea I most want you to leave today with, cold: Python lists are indexed starting at zero. The first item is at position 0, not 1. I want you to say that out loud with me once: 'the first item is at index zero.'"

The idea — both index systems on the same five items

Point to the board diagram from your setup checklist
 index:    0        1          2         3       4
 value:  "pen"  "notebook"  "stapler"  "tape"  "marker"
 neg idx: -5       -4         -3        -2       -1

The first item is inventory[0], not inventory[1]. inventory[-1] is the last item, counting backward — no need to compute len(inventory) - 1. Valid indices for this five-item list are only 0 through 4 (and -5 through -1).

This is the pre-drawn numbered box diagram from the Setup Checklist — positive indices 0–4 and negative indices -5 to -1 mapped onto the same five items. The guide: "this single visual does more for Exercise 2 than any amount of verbal explanation." Have the class say "the first item is at index zero" out loud once.

Live-code — Exercise 2

# --- Exercise 2 --- inventory = ["pen", "notebook", "stapler", "tape", "marker"] print(inventory[0]) print(inventory[-1]) mid = len(inventory) // 2 print(inventory[mid])

inventory[0] is pen (first, index 0 — not 1); inventory[-1] is marker (last); mid = len(inventory) // 2 is 5 // 2 = 2, so inventory[2] is stapler — deliberately not hardcoded as inventory[2].

Line-by-line: - inventory[0] — the first item, at index 0. Say explicitly, again: not index 1 — the single most common source of off-by-one bugs for the rest of the semester, worth over-emphasizing now. - inventory[-1] — negative indexing: -1 means "the last item," counting backward from the end. Say explicitly that it avoids needing to compute len(inventory) - 1 just to reach the last element, which is what you'd have to do in many other languages. - mid = len(inventory) // 2 — floor division from Module 04/05, doing real work: for a 5-item list, 5 // 2 is 2, and inventory[2] is "stapler", the true middle of an odd-length list. Deliberately not hardcoded as inventory[2] — if the list's length changes later this line still finds the middle, while a hardcoded 2 would silently become wrong. Common mistakes: writing inventory[1] expecting the first item (have the student recount using the board diagram themselves); writing inventory[5] expecting the last item — raises IndexError (next slide); hardcoding inventory[2] for the middle instead of computing it from len(). Check for understanding (guide, verbatim parenthetical): "For a list with 7 items, what index is the true middle, and what expression computes it without hardcoding? (7 // 2 = 3, so inventory[3] — get a student to compute this live, not just state the formula, to confirm the reasoning transfers to a different length.)"

Exercise 3 · 8 min · 0:19–0:27

Slicing

Teaching goal: slice notation for extracting a sub-portion of a list — [start:stop], open-ended slices, and step slices — building directly on Exercise 2's indexing. Say to the class (verbatim): "Indexing gets you one item. Slicing gets you a range of items — a new, smaller list, cut out of the original. Three flavors today."

Live-code — Exercise 3

# --- Exercise 3 --- inventory = ["pen", "notebook", "stapler", "tape", "marker"] print(inventory[:3]) print(inventory[-2:]) print(inventory[::2])

[:3] = "everything up to, but not including, index 3" → indices 0, 1, 2 (stop is exclusive). [-2:] = second-to-last through the end. [::2] = every second element from index 0 → indices 0, 2, 4.

Line-by-line: - inventory[:3] — no start (defaults to the beginning), stop of 3: "everything up to, but not including, index 3." Slow down here: the stop value is exclusive — [:3] gives indices 0, 1, 2, three items total, not including whatever's at index 3. This "stop is exclusive" rule is consistent with range() and is worth naming as a general Python convention, not a one-off quirk of slicing. - inventory[-2:] — no stop (defaults to the end), start of -2: "starting from the second-to-last item, go to the end" — combines negative indexing with open-ended slicing. - inventory[::2] — step slicing: two colons, "no explicit start, no explicit stop, but a step of 2" — take every second element, starting from index 0. Walk through the indices: 0, 2, 4 → "pen", "stapler", "marker". Common mistakes: expecting inventory[:3] to include the item at index 3 ("tape") — have the room count the returned list's length (3) against the slice's stop value (3): the stop number equals the count of items you get when starting from index 0. Confusing [::2] (step slicing) with [:2] (first two elements) — write both side by side if it surfaces. Check for understanding (guide, verbatim parenthetical): "Without running it, what does inventory[1:4] return? (Indices 1, 2, 3 → ['notebook', 'stapler', 'tape'] — three items, again matching the 'count = stop − start' shortcut from above, now with an explicit start.)"

Expected output

['pen', 'notebook', 'stapler']
['tape', 'marker']
['pen', 'stapler', 'marker']

Modify in Place

Teaching goal: list methods that change the list in place — .append(), .remove(), .sort() — and the crucial fact that these methods don't return a new list; they mutate the original. Say to the class (verbatim): "Three methods that change the list itself, permanently, right where it lives in memory — not by giving you back a new, separate list. Print after every single step so you can watch the same variable change shape three times in a row."

The idea — mutate the target, hand back nothing useful

Say it once, explicitly

inventory.append("envelope"), not inventory = inventory.append("envelope"). .append() returns None, so assigning its result back to inventory would destroy the list, replacing it with None.

Not every method works like Module 07's pure functions. Some — like these three — modify their target and hand nothing useful back. .remove() takes a value to search for and delete, not an index. .sort() reorders in place, same "modifies, doesn't return a new list" behavior.

This card is the guide's line-by-line for Exercise 4, condensed. The inventory = inventory.append(...) trap is worth demonstrating live as a deliberate broken example (next-but-one slide), since it's a very natural instinct coming from Module 07's "functions return values" lesson.

Live-code — Exercise 4

# --- Exercise 4 --- inventory = ["pen", "notebook", "stapler", "tape", "marker"] inventory.append("envelope") print(inventory) inventory.remove("tape") print(inventory) inventory.sort() print(inventory)

Print after every step and watch the same variable change shape three times: .append("envelope") adds to the end; .remove("tape") deletes the first item matching that value; .sort() reorders alphabetically in place.

Line-by-line: - inventory.append("envelope") — adds "envelope" to the end of the list, in place. Note the syntax: inventory.append(...), not inventory = inventory.append(...) — the second form is a real trap: .append() returns None, so assigning its result back would destroy the list, replacing it with None. Demonstrate live (next slide). - inventory.remove("tape") — removes the first item matching the given value (not a position) — contrast explicitly with indexing: .remove() takes a value to search for and delete, not an index to remove by position. - inventory.sort() — sorts the list alphabetically (for strings) in place, same "modifies, doesn't return a new list" behavior as .append(). Exercise 5 · 10 min · 0:35–0:45

Tuple Comparison

Teaching goal: the mutable-vs-immutable distinction between lists and tuples — genuinely the second-most-important idea in this lab, and directly tied to try/except, a new syntax pattern for gracefully handling an error instead of letting the program crash. Say to the class (verbatim): "Everything so far has been a list — changeable, or 'mutable.' Now, a tuple: parentheses instead of square brackets, and fundamentally unchangeable once created — 'immutable.' We're going to try to break that rule on purpose, catch the resulting error gracefully instead of crashing, and think about why immutability is actually a feature, not a limitation, for something like GPS coordinates."

The idea — try/except is new syntax today

A different relationship with errors

A tuple is created with parentheses (...) and, once created, its contents cannot be changed, added to, or removed from.

try: marks code that might raise an error; if it does, instead of crashing, Python jumps to the matching except block. This is the first time this semester an error is deliberately anticipated and handled rather than treated purely as a bug to fix. except TypeError as e: — the as e captures the exception object so its message can be printed.

The guide flags this as the second-most-important idea in the lab. Say explicitly: sometimes an error is an expected, normal possibility your program should gracefully respond to, not always a mistake to eliminate. "Immutable" is a genuinely new vocabulary word this module — and it means only that reassignment of an element is disallowed; tuples can still be read, accessed, and printed freely.

Live-code — Exercise 5

# --- Exercise 5 --- coords = (40.7128, -74.0060) # New York City try: coords[0] = 99 except TypeError as e: print(f"TypeError caught: {e}") print("Tuples are immutable — useful for coordinates because a " "location's latitude/longitude shouldn't be accidentally " "reassignable partway through a program.") print(coords)

The assignment coords[0] = 99 raises TypeError: 'tuple' object does not support item assignment; the except block catches it, prints the message, and the program keeps running. The final print(coords) confirms the tuple is unchanged.

Line-by-line: - coords = (40.7128, -74.0060) — parentheses (...), not square brackets, create a tuple — syntactically similar to a list, but with a fundamentally different guarantee: once created, its contents cannot be changed, added to, or removed from. - try: / except TypeError as e: — new syntax today. try marks a block that might raise an error; if it does, Python jumps to the matching except block instead of crashing. First time this semester an error is deliberately anticipated and handled. - coords[0] = 99 — attempting to reassign the first element, exactly like a list assignment would allow — but tuples don't support this at all, regardless of index, raising TypeError: 'tuple' object does not support item assignment. - except TypeError as e: — as e captures the actual exception object, so print(f"TypeError caught: {e}") shows the exact error text without crashing. - The explanation printed inside the except block is the exercise's actual required deliverable — a real conceptual point: coordinates are a natural fit for tuples because a location's latitude and longitude are conceptually a fixed pair that shouldn't drift or be partially edited; immutability turns an accidental modification into a loud, catchable error instead of a silent, corrupted location. - print(coords) after the try/except — confirms the tuple is genuinely unchanged, since the assignment inside try never took effect. Note the printed tuple shows -74.006, not -74.0060 — Python drops the trailing zero when displaying the float (they are the exact same numeric value); a ten-second aside if a sharp student notices. Common mistakes: omitting try/except and running coords[0] = 99 directly (program crashes with an unhandled TypeError and stops — run it both ways side by side); a bare except: with no type (works, but catching all errors can hide real bugs — catch the specific TypeError); confusing "immutable" with "can't be printed / read" — only reassignment of an element is disallowed. Check for understanding (guide, verbatim parenthetical): "If tuples can't be changed, why not just always use lists for everything, and skip tuples entirely? (A good answer names at least one of: immutability as a safety guarantee against accidental modification, e.g. for something that should behave like a fixed record; or the fact that tuples signal intent — 'this collection of values is meant to stay fixed' — to anyone reading the code later, which lists don't communicate.)"

Teaching goal: use .append() inside a loop to build an entirely new list from an existing one — a new shape of accumulator pattern: instead of accumulating into a single number, accumulate into a growing list. The idea — the empty starting value matches the shape you're building

Two points

discounted = [] is initialize, exactly like Module 06's total = 0 — but the "empty" starting value is an empty list, not zero. A running number starts at 0; a growing list starts at [].

round(price * 0.9, 2) — round() is new here and actually changes the stored numeric value (unlike an f-string format spec, which only affects display), which matters because this value is going into a list. The original prices list is left completely untouched — a deliberate choice: you likely need both the original and the discounted price.

This card is the guide's line-by-line for Exercise 7, condensed. Contrast with Exercise 4's .append()/.remove()/.sort(), all of which did modify their list in place.
