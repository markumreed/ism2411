Learning objectives

By the end of this 75-minute session, students should be able to:

  • Write the accumulator pattern from scratch: initialize a variable before the loop, update it inside the loop, use the final value after the loop.
  • Explain why total must be initialized to 0 before the loop, not inside it — and why doing it wrong either crashes or silently resets on every iteration.
  • Combine an accumulator with an if check inside the loop body to filter or conditionally update.
  • Use break to exit a loop early and continue to skip an iteration, and articulate the difference between the two.
  • Convert a for loop into an equivalent while loop, and explain the tradeoffs of each.

Exercise 1 · 10 min · 0:05–0:15

Sum a List

Teaching goal: the accumulator pattern, in its simplest form — this is the exercise to slow all the way down for, since it's the load-bearing idea of the whole lab. Say to the class (verbatim): "Three steps, always in this order: initialize a variable before the loop starts, update it on every pass through the loop, use the final value after the loop ends. I want you to say those three words back to me — initialize, update, use — because you're going to apply this exact skeleton six more times today."

Live-code — Exercise 1

# --- Exercise 1 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] total = 0 # initialize for sale in sales: total += sale # update print(f"Total: ${total}") # use

Three steps, always in this order: initialize before the loop, update inside it, use the final value after. Run it — the total is $1400.

Line-by-line: - total = 0 — initialize, before the loop. This has to happen before for sale in sales: starts, not inside it — say explicitly why: if this line were inside the loop body, total would be reset to 0 on every single pass, and you'd only ever end up with the last sale's value, not a running sum. This is the single most important sentence in this lab — consider writing it on the board verbatim. - for sale in sales: — a for loop over a list. sale is a loop variable: on the first pass it holds sales[0] (120), on the second sales[1] (80), and so on, automatically, one element at a time, until the list is exhausted. Point out: sale is not a keyword — it's a name you chose and could be x, s, amount; naming it the singular of the list name is a readability habit, not a rule. - total += sale — update, inside the loop, indented to show it's part of the loop body. += means "add sale to whatever total already holds, and store the result back in total." Runs eight times, once per element. - print(f"Total: ${total}") — use, after the loop, not indented. The indentation (back to the left margin, same level as total = 0) is what tells Python it runs once, after the loop finishes, not once per iteration. Indenting it to match the loop body gives eight separate Total: ... lines — a good deliberate demo if you have a spare 30 seconds. Common mistakes: initializing total inside the loop (resets to 0 every pass, final value is just the last element 215) — demonstrated on the next slide; forgetting += and writing total = sale (same failure mode); indenting the final print() into the loop body. Check for understanding (guide, verbatim parenthetical): "If sales had 50 items instead of 8, what — if anything — would need to change about this code? (Nothing — the loop automatically runs once per item regardless of list length; this is worth stating explicitly as the payoff of using a loop at all, versus eight individual hardcoded additions.)"

Deliberately broken — total re-initialized inside the loop

# --- Exercise 1 (BROKEN: total reset to 0 on every pass) --- sales = [120, 80, 250, 175, 90, 410, 60, 215] total = 0 for sale in sales: total = 0 # BUG: this belongs BEFORE the loop, not inside it total += sale print(f"Total: ${total}")

Move the total = 0 line inside the loop and run it — the answer is now $215, the last element, not $1400. No crash, just a silently wrong number. This is Exercise 1's central teaching point — worth seeing fail before it's understood as correct.

Teaching goal: show the accumulator's single most important rule by breaking it — initialize before the loop, never inside. Line-by-line: with total = 0 inside the loop body, every pass wipes total back to 0 and then adds only that pass's sale. After the final pass total holds 0 + 215 = 215 — just the last element. Output: Total: $215. Common mistakes: this is the mistake — demonstrate it live, then move the line back out above for sale in sales: and re-run to get $1400. Exercise 2 · 6 min · 0:15–0:21

Average

Teaching goal: track a second accumulator (a count) alongside the first, and combine them after the loop — the same skeleton, doubled. Say to the class (verbatim): "Average needs two numbers: the total, and how many items there were. We're tracking both inside the same loop, then dividing after the loop ends — not using len() or sum(), on purpose, so the accumulator pattern is doing all the work."

Live-code — Exercise 2

# --- Exercise 2 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] total = 0 # initialize count = 0 # initialize for sale in sales: total += sale # update count += 1 # update average = total / count # use print(f"Total: ${total}") print(f"Count: {count}") print(f"Average: ${average:.2f}")

Two accumulators in one loop: total sums values, count counts iterations. The division happens after the loop, using both final values. No len() or sum() — on purpose.

Line-by-line: - count = 0 — a second accumulator, initialized alongside total, before the loop. - count += 1 — inside the loop, incrementing by exactly 1 on every pass, regardless of the sale's value — contrast explicitly with total += sale, which adds a different amount each time. count is counting iterations; total is summing values. Two different jobs, same pattern. - average = total / count — runs after the loop, using both accumulators' final values. It could not run correctly inside the loop, since count and total aren't at their final values until the loop finishes — flag this, since some students will be tempted to compute a "running average" inside the loop out of habit. Common mistakes: computing average inside the loop body (eight different intermediate "averages"; the last one coincidentally equals the right answer, hiding that the other seven lines were wrong); dividing by len(sales) instead of count — not wrong output-wise, but it defeats the exercise's stated constraint, and Exercise 6 depends on students being comfortable tracking values manually. Check for understanding (guide, verbatim parenthetical): "Why do we need a separate count variable — why can't we just use total for both the sum and the count? (Because they're fundamentally different quantities that happen to both start at 0 — total needs the actual sale amounts added in, count needs a flat 1 added in regardless of amount; conflating them would corrupt both.)"

Exercise 3 · 8 min · 0:21–0:29

Max

Teaching goal: a third accumulator variant — instead of adding on every pass, conditionally replace the tracked value only when a new one is larger. Say to the class (verbatim): "Same three-step skeleton, but the update step is different: instead of always adding, we only update when we find something bigger than what we've seen so far."

The idea — conditional replace, and why current_max = 0 is a shortcut

Say it once, explicitly

The update step is now conditional: if sale > current_max: then current_max = sale. On passes where the if is False, nothing happens — unlike the sum, where every pass changed total.

current_max = 0 works only because every sale here is positive, so 0 is guaranteed smaller than any real sale and gets replaced on the first comparison. If the list could contain negatives, a list of all-negative sales would wrongly report a max of 0. The robust, general-purpose alternative: initialize to the list's first element, sales[0].

This card is the guide's line-by-line for the current_max = 0 initialization plus its explicit note that sales[0] is the more robust pattern. It is also the first time this semester a conditional sits inside a loop — a structural first that Exercises 4 and 7 lean on harder.

Live-code — Exercise 3

# --- Exercise 3 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] current_max = 0 # initialize for sale in sales: if sale > current_max: # compare current_max = sale # update, conditionally print(f"Largest sale: ${current_max}")

Trace the first three sales by hand: 120 > 0 → update to 120; 80 > 120 → False, no update; 250 > 120 → update to 250. Final answer: $410.

Line-by-line: - current_max = 0 — initialized to 0 here specifically because all sales in this list are positive, so 0 is guaranteed smaller than any real sale and will always get replaced on the first comparison. Flag as a real limitation: if the list could contain negative numbers, initializing to 0 would be wrong — a list of all-negative sales would incorrectly report a max of 0. The safe, general-purpose alternative is to initialize current_max to the list's first element (sales[0]). - if sale > current_max: — the comparison step, using Module 05's if syntax, now nested inside a loop for the first time this semester. Call this out as a structural first: a conditional inside a loop, exactly the combination Exercises 4 and 7 lean on harder. - current_max = sale — the conditional update: only runs on passes where the if above was True. Walk through the first three sales aloud: 120 > 0 → update to 120; 80 > 120 → False, no update; 250 > 120 → update to 250. Common mistakes: updating current_max unconditionally every pass (forgetting the if, or misindenting so the assignment isn't inside the if) — silently sets current_max to the last element (215) every time; with this list the true max 410 is not last, so the bug is very visible. Using >= instead of > — harmless here (same answer), but worth a quick "when would it matter?" aside (only if also tracking which index was the max, and ties mattered). Check for understanding (guide, verbatim parenthetical): "Using the same skeleton, how would you track the minimum instead of the maximum — what two things change? (Initialize to a very large number, or to sales[0], instead of 0; flip the comparison to <. Getting a student to articulate both changes confirms they understand the pattern's moving parts, not just this one instance of it.)"

Exercise 4 · 7 min · 0:29–0:36

Filtered Count

Teaching goal: combine two accumulators with a filtering if, directly previewing Exercise 7's structure — this is the exercise that makes the "if inside a loop, with an accumulator" combination feel routine rather than novel. Say to the class (verbatim): "Now we're counting and summing, but only for sales that pass a filter — over $100. Notice this uses everything from the last three exercises at once."

The idea — two levels of indentation

Point at the screen while you say this

if sale > 100: is inside the loop body — one level of indent. Both += lines are inside the if body — two levels of indent.

Get that indentation wrong and the filter either does nothing (both += lines back at loop level → every sale counted) or excludes everything. Sales at or below $100 are simply skipped for both counters, since neither line inside the if body runs when the condition is False.

This card is the guide's line-by-line for Exercise 4, condensed — the double-indentation point is the whole lesson. Both accumulators are initialized before the loop, same as Exercise 2, but this time both updates live one level deeper, inside the if.

Live-code — Exercise 4

# --- Exercise 4 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] count_over_100 = 0 # initialize total_over_100 = 0 # initialize for sale in sales: if sale > 100: # filter count_over_100 += 1 # update total_over_100 += sale # update print(f"Sales over $100: {count_over_100}") print(f"Total of those sales: ${total_over_100}")

Compare the filtered total $1170 against Exercise 1's full-list total $1400 — if a student gets $1400 here, that's the tell that the total_over_100 += sale line slipped back out to loop level.

Line-by-line: - Two accumulators initialized before the loop, same as Exercise 2 — but this time both updates are indented one level deeper, inside the if, not directly inside the for. Point at this on screen: if sale > 100: is inside the loop body (one level of indent), both += lines are inside the if body (two levels). Get this indentation wrong and the filter either does nothing or excludes everything. - Both accumulators update together, only for sales that pass the filter — sales at or below $100 are simply skipped for both counters, since neither line inside the if body runs when the condition is False. Over $100: 120, 250, 175, 410, 215 → five sales summing to 1170. Common mistakes: indenting total_over_100 += sale back out to the loop level — sums every sale regardless of the filter, silently disconnecting it from count_over_100 (which stays filtered); a $1400 here vs. $1170 is the tell. Exercise 5 · 10 min · 0:36–0:46

break / continue

Teaching goal: two new loop-control keywords that change a loop's normal top-to-bottom, every-iteration behavior — continue skips the rest of the current pass, break exits the entire loop immediately. Say to the class (verbatim): "So far every loop has run through the whole list, every time. These two keywords change that. continue says 'skip the rest of this one pass, move to the next item.' break says 'stop the loop completely, right now, don't look at any more items.' Very different, easy to confuse — let's build intuition by using both in the same loop."

The idea — skip one pass vs. stop the whole loop

The one contrast that matters

continue does not stop the loop — it only stops the current pass through the loop, jumping straight to the next item. Every line below it is skipped for that pass.

break exits the loop immediately and completely. After a break there is no "next iteration" — the remaining items are never looked at.

Trace it with the class, sale by sale, since this is the exercise's real payoff: 120 → passes both checks, prints $120. 80 → continue, skipped, nothing printed. 250 → prints $250. 175 → prints $175. 90 → continue, skipped. 410 → triggers break, prints the alert, loop ends here — the remaining sales (60, 215) are never even looked at.

Live-code — Exercise 5

# --- Exercise 5 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] for sale in sales: if sale <= 100: continue # skip small sales if sale > 400: print(f"Alert: outlier found — ${sale}. Stopping.") break # stop entirely print(f"${sale}")

The output has exactly four lines, not more. After 410 triggers break, the loop is finished — 60 and 215 are never examined. Ask someone to explain out loud why.

Line-by-line: - if sale <= 100: continue — for any sale of $100 or less, continue immediately jumps to the next iteration, skipping every line below it for this pass — specifically print(f"${sale}") never runs for these values. continue does not stop the loop, it only stops the current pass through it. - if sale > 400: ... break — for any sale over $400, print the alert, then break — this exits the loop immediately and completely; no further sales are examined at all, even ones that would also be over $100 or under $400. The crucial contrast with continue: after a break, the loop is entirely finished; there's no "next iteration." - print(f"${sale}") — the fallback: only reached by sales that are both over $100 (didn't trigger continue) and not over $400 (didn't trigger break). Hand-trace: 120 → prints $120. 80 → continue. 250 → $250. 175 → $175. 90 → continue. 410 → break, prints the alert, loop ends — 60, 215 never looked at. Common mistakes: expecting the loop to continue after break, printing 60 and 215 too — the single most common misconception; confirm the output has exactly four lines. Confusing which keyword does which — walk them through re-tracing by hand rather than just naming the correct keyword. Placing the continue check after the break check — with this data, order changes nothing (the two conditions, sale <= 100 and sale > 400, can never both be true for one value); contrast with Module 05 Exercise 1's discount tiers, where order did matter. Check for understanding (guide, verbatim parenthetical): "If I removed the break entirely, keeping only the continue, what would the output be for the full list? ($120, $250, $175, $410, $215 — every sale over $100 gets printed now, including $410 and $215, since nothing stops the loop early anymore; only the <= 100 sales are still skipped.)"

$250
$175

Exercise 6 · 8 min · 0:46–0:54

while Loop Rewrite

Teaching goal: re-implement Exercise 1's sum using a while loop and a manually managed index — direct, felt comparison of the two loop styles, including the tedium of manual index management that for loops hide. Say to the class (verbatim): "Same sum as Exercise 1, same final answer — but built with a while loop instead of a for loop. You're going to feel the difference immediately: while doesn't know how to walk through a list on its own. You have to manage the position yourself, with an index variable."

The idea — while makes you do by hand what for does for free

Two things you now have to manage yourself

An index — i = 0, initialized before the loop, a running position counter. And an explicit increment — i += 1 inside the loop body. A for sale in sales: loop handles both automatically.

i += 1 is the line students most often forget — and forgetting it causes an infinite loop: i never grows, i < len(sales) stays True forever, the program hangs. Interrupt with Ctrl+C, then point at the missing line.

This card is the guide's line-by-line for Exercise 6, condensed. The tedium of manual index management is the lesson — this is intentionally the most tedious exercise in the lab. Don't feel obligated to type every line slowly if the room is already following the accumulator pattern well.

Live-code — Exercise 6

# --- Exercise 6 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] total = 0 # initialize i = 0 # initialize the index while i < len(sales): total += sales[i] # update, using the index to look up the value i += 1 # update the index — THIS LINE IS ESSENTIAL print(f"Total: ${total}")

Same final answer as Exercise 1 — $1400 — but built the hard way. len(sales) is 8; the loop runs for i = 0, 1, ..., 7 and stops the moment i reaches 8, since 8 < 8 is False.

The idea — recomputed every pass, and where print() belongs

Two structural points

The whole if/elif/else block is inside the loop, so it runs fresh from scratch on every pass, deciding a new discount for each sale. Unlike the accumulators in Exercises 1–4, discount is not carried between iterations — it has no memory of the previous sale.

The print() is inside the loop too — one line of output per sale. Contrast with Exercises 1–4, where print() ran once, after the loop, on an accumulated value. "Inside the loop (one line per item)" vs. "after it (one summary line)" is a real design decision every loop-based script will require.

Stretch 1 · 8 min · 1:02–1:10

Running Total Report

Teaching goal: a bank-statement-style running total — print the accumulator's value during the loop, at every step, not just at the end — plus a genuinely interesting discussion point about what "count how many times it crossed $500" even means for strictly increasing data. Say to the class (verbatim): "One more accumulator variation: print the running total after every single transaction, like a bank statement, instead of only printing the final sum once at the end."

The idea — a flag is a new accumulator shape

What's new here

running_total += sale then immediately print(...) inside the loop — the printed value updates on every pass, unlike Exercise 1 where the total was revealed once at the end.

crossed_500 is a flag: a boolean that starts False and flips to True the first (and only the first) time the total exceeds $500. Not a running sum or a count of values — a one-time "has this happened yet" tracker. Because every sale is positive, running_total only ever goes up, so it can cross $500 exactly once — crossings will always be 1 for this dataset.

Worth raising as an explicit discussion point: since every sale is positive, running_total is monotonically increasing. Ask the room: "under what circumstances could this count be something other than 1?" (If the list contained negative values — refunds/returns — the running total could dip back below $500 after crossing, then cross again. With all-positive data the flag guard is still good practice, but the "count" is a bit of a red herring on this dataset — a good moment for honest critique of an exercise's design.)

Live-code — Stretch 1

# --- Stretch 1 --- sales = [120, 80, 250, 175, 90, 410, 60, 215] running_total = 0 crossed_500 = False crossings = 0 for sale in sales: running_total += sale print(f"${sale} -> running total: ${running_total}") if running_total > 500 and not crossed_500: crossings += 1 crossed_500 = True print(f"Number of transactions that first pushed the running total above $500: {crossings}")

Without the not crossed_500 guard, crossings would increment on every pass after the total first crosses $500 (five of the eight passes), reporting 5 instead of 1.

The idea — a loop inside a loop

Read the shape

The outer loop runs once per row (i from 1 to 5). For each row, the inner loop runs completely — once per column (j from 1 to 5) — before the outer loop moves on. 5 × 5 = 25 inner iterations total.

row += f"{i*j:4}" builds one row as a string (the :4 pads each number to 4 characters so columns line up), and print(row) — outside the inner loop, inside the outer — emits it once per row.

Business-relevant extension, stated verbally: swap the multiplication table for 5 products × 3 quantity tiers and the same nested-loop shape generates a full price list. Appendix A has the working price-list version. This whole segment is optional take-home — a separate topic from the accumulator pattern.

Live demo (if time allows) — Stretch 2

for i in range(1, 6): row = "" for j in range(1, 6): row += f"{i*j:4}" print(row)

Five rows, five columns, right-aligned in 4-character fields. The inner loop finishes entirely for each value of i before print(row) runs and the outer loop advances.

Line-by-line: - for i in range(1, 6): — the outer loop, i taking 1, 2, 3, 4, 5 (range(1, 6) stops before 6). - row = "" — reset the row string at the start of each outer pass (an accumulator, re-initialized once per row — same "initialize before the loop that updates it" rule as Exercise 1). - for j in range(1, 6): — the inner loop, running fully (j = 1..5) for every single value of i. - row += f"{i*j:4}" — append i*j formatted into a 4-wide field so columns align. - print(row) — outside the inner loop, inside the outer: one printed line per row. Common mistakes: putting print(row) inside the inner loop (prints a partial row 25 times); forgetting to reset row = "" each outer pass (every row keeps growing).
