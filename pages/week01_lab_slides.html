75-minute session. This is the only lab all semester with zero code in it, and that is deliberate: everything from Module 02 onward assumes students already have a rock-solid mental model of what a file is, where it lives, and how a computer finds it. Because there is no code to anchor the room's attention, this session lives or dies on your pacing and your questions — the content itself (nine vocabulary words, three RAM/storage scenarios) is thin enough to blow through in fifteen minutes if you let it. Don't. This guide over-provisions discussion prompts and extra worked examples specifically so you have material to slow down with. The two runnable shell blocks in this deck (Exercise 2's folder build, Exercise 5's tree reconstruction) are conveniences for demoing the file-system ideas on the projector — the guide itself has students work on paper / in Finder, and either path is fine.

Learning objectives

By the end of this 75-minute session, students should be able to:

  • Read any absolute file path and correctly label its root, directory chain, filename, and extension.
  • Explain, in their own words, what CPU, RAM, storage, file, directory, path, extension, program, and interpreter each mean — and how they relate to each other as one system.
  • Draw the directory tree implied by a set of file paths, and write a correct relative path between two files in that tree.
  • Classify a real-world "something went wrong" scenario as a RAM problem, a storage problem, or neither.
  • Identify a repetitive spreadsheet task as a plausible automation candidate — without yet knowing how to build the automation.
The verbs matter. Objective 2 ("as one system") is the real target of Exercise 3 — nine connected ideas, not nine flashcards. Objective 4 (RAM vs. storage vs. neither) is what Exercise 6 tests, and it is the misconception this whole lab is built to correct.

Exercise 1 · 8 min · 0:05–0:13

Trace a Real File Path

Teaching goal: anchor the abstract idea of "a path" in something concretely on the student's own machine, before moving to hypothetical examples. Say to the class (verbatim): "Open Finder or File Explorer right now. Go to your Downloads folder — everyone has files in there. Pick any one file, right-click it, and choose Get Info on a Mac or Properties on Windows. There's a full path shown there. Copy it down." Do, live on the projector: Demo this once yourself first so students see exactly which menu item to click (this is the single most common place to lose five minutes — half the room will click the wrong thing if you don't show it). Then walk your own example path on screen and label each segment out loud. Have every student write their own labeled path (their own Downloads file, not yours) — this individual repetition, immediately after your demo, is what makes the concept land.

The idea — anatomy of a path

Concept

Every file has one full address. Example: /Users/yourname/Downloads/syllabus.pdf

Root — / — the very top of the entire filesystem. On Windows this is a drive letter like C:\ instead — worth mentioning explicitly since roughly half the room is on Windows.

Directory chain — Users/yourname/Downloads/ — the sequence of nested folders you pass through to reach the file: each one lives inside the one before it.

Filename — syllabus  ·  Extension — .pdf — tells the OS (and every application) what kind of file this is and which program opens it by default.

Line by line, pointing at each segment as you say it: - Root / — top of the whole filesystem; Windows equivalent is C:\, and the backslash-vs-forward-slash difference is a genuine platform difference they will need to remember. - Directory chain Users/yourname/Downloads/ — the sequence of folders passed through; stress that it is a chain of nested folders, not a flat list. That nesting concept is the entire foundation for Exercise 5. - Filename syllabus — the human-facing name. - Extension .pdf — the last segment of the path; tells the OS/apps what kind of file it is and which program opens it.

Knowledge check

In /Users/mia/Downloads/report.pdf, the directory chain Users/mia/Downloads/ is best described as…

A chain of nested folders — Downloads is inside mia, which is inside Users, which is inside the root /. That nesting is exactly what you'll reconstruct as a tree in Exercise 5.

Check for understanding (guide): cold-call 2–3 students to read their labeled path out loud, and listen specifically for whether they say "directory chain" as a chain of nested folders (not just a flat list) — that nesting concept is the entire foundation for Exercise 5. The data-answer here (B, "a chain of nested folders, not a flat list") is that same listening target.

Common student confusion

Watch for

Windows students writing C:\Users\name\Downloads\file.pdf and being unsure whether C:\ counts as "the root" the same way / does on Mac — confirm explicitly that yes, it is the Windows equivalent, and the backslash-vs-forward-slash difference is a genuine platform difference.

Students who copy a path with no extension (a folder, or a file whose extension is hidden because their OS hides known extensions by default) — pause and use it: "why might an OS hide extensions by default, and what problem can that cause?" Answer: it looks cleaner for non-technical users, but people then can't tell a real .pdf from a disguised invoice.pdf.exe — a real security angle worth 30 seconds.

The hidden-extension case is worth deliberately steering into if you see it — it is the most memorable version of "the extension is load-bearing information."

Exercise 3 · 15 min · 0:19–0:34

Nine Vocabulary Terms

Teaching goal: nine terms that form one connected mental model, not nine disconnected flashcards — the goal is for students to be able to explain how the terms relate, not just recite definitions. Say to the class (verbatim): "Nine terms. I'm not going to just read you definitions — for each one, I want a volunteer to take a first attempt, out loud, before I confirm or correct it. Getting it slightly wrong out loud and then hearing the correction is how this actually sticks." Do: work through each term as a mini-dialogue, not a lecture. For each term: ask for a volunteer definition first, then confirm/refine using the reference definition, then use the one-line "why it matters" hook to connect it to the next term. Then have students write their own one-sentence definitions for all nine, in their own words, individually — that is the exercise's actual required deliverable, and it should happen after the group discussion, not instead of it.

The nine terms — one connected model

TermReference definitionConnects to
CPUThe chip that executes your program's instructions, one at a time."Executes" — but from where does it read those instructions?
RAMFast, temporary memory where running programs and open files live; clears when the computer shuts down.The CPU pulls from RAM constantly — it's the workspace.
StorageSlower, permanent memory where files live even when the computer is off.RAM's contents come from storage when a program starts.
FileA named sequence of bytes stored on disk.Files live in directories — never floating alone.
DirectoryA container for files and other directories; also called a folder.Directories nest — a directory can contain other directories.
PathThe full address of a file within the directory hierarchy.This is Exercise 1's labeled string, formalized.
ExtensionThe suffix after the dot in a filename that tells the OS/apps what kind of file it is.The last segment of a path — connects back to Exercise 1.
ProgramA set of instructions that tells the computer what to do.Programs are themselves just files, until they're running.
InterpreterThe program that reads and executes another program's instructions, one line at a time — Python's interpreter, specifically, for this course.This is what runs every script you'll write starting Module 02.
Work each row as a mini-dialogue: volunteer attempt first, then confirm with the reference definition, then use the "Connects to" hook to bridge to the next term. Common mistake: a definition that sounds identical to the reading — ask them to explain it as if to a friend with zero CS background, and have them write that version down.

The whole story in one breath

Say this verbatim once all nine are covered

"Your files live in storage, organized into nested directories, each reachable by a path. When you run a program, the interpreter reads that program's instructions from storage and the CPU executes them — and while it's running, everything it's actively working with sits in RAM, not storage, which is why unsaved work disappears if the power cuts. That's the entire mental model. Every module this semester is a variation on some piece of that sentence."

This is the payoff of the table — do not skip it. Say it as one connected sentence, slowly, then have students write their own nine one-line definitions individually (the required deliverable). If a sharp student raises "process vs. program," it's a good preview hook for later but not required vocabulary this week.

Knowledge check

"Unsaved work vanishes when the laptop dies" and "a missing file triggers file not found" — how do these two failures relate?

Two different failure modes. Unsaved work lived only in RAM (fast, temporary, cleared on power loss). A missing file is a storage matter — the bytes aren't on disk where you're looking. Conflating them is the single most common misconception this exercise exists to correct, and it's exactly what Exercise 6 tests.

Check for understanding (guide): ask the room to raise a hand if they can now explain, without notes, why unsaved work disappears when a laptop dies — but not why a missing file causes a "file not found" error. These are two different failure modes, RAM vs. storage, and conflating them is the single most common misconception this exercise is designed to correct — it's also exactly what Exercise 6 tests. The data-answer (C) is that distinction stated directly.

Common student mistakes

Watch for

Confusing "program" and "process" (a process is a program that's currently running) — not required vocabulary this week, but if a sharp student raises it, it's a good preview hook for later.

Writing a definition of RAM or storage that's just a memorized textbook sentence rather than their own phrasing — if a definition sounds identical to the reading, ask them to explain it to you as if to a friend with zero CS background, and have them write that version down instead.

The "explain it to a friend with zero CS background" move is the fastest way to convert a memorized sentence into genuine understanding — use it liberally in this segment.
Exercise 4 · 10 min · 0:34–0:44 · pair discussion

Automation Reflection

Teaching goal: get students recognizing automatable patterns in tasks they already do, without expecting them to know how to build the automation yet — this is a motivation exercise, not a skills exercise. Say to the class (verbatim): "Turn to the person next to you. Each of you names three things you currently do in Excel — or any repetitive task, doesn't have to be Excel — that take more than ten minutes. For each one, discuss: could a program that runs in a few seconds do this instead? You don't need to know how yet — just whether the task has the right shape." Do: give pairs 6 minutes to discuss and write down three tasks each (or three shared ones), then use the last 4 minutes to have 2–3 pairs share one example each with the whole room.

What makes a task the right shape?

Concept

Two properties make a task automatable:

Repetition — the same steps, over and over.

Clear rules — a human doesn't have to use judgment at each step.

Seed examples if a pair is stuck: (1) copying last week's sales numbers into a summary tab every Monday; (2) reformatting a CSV export so the columns match a template; (3) cross-checking two spreadsheets by eye for rows that don't match.

The distinguishing question to drill into during share-out: "What makes this task the kind of thing a computer is good at?" Look for answers that name repetition and clear rules — those two properties are the actual learning goal, more than the specific examples. A task that needs human judgment at every step (e.g. "deciding which client to prioritize") is a good contrast: judgment-heavy tasks are harder to automate, and that distinction is worth surfacing rather than correcting away.

Knowledge check

Given unlimited time to learn Python, which of your three tasks should you automate first?

The most repetitive, rule-based task — the one with the right shape — not necessarily the one that eats the most hours. A slow task that needs judgment at every step is a bad first automation target.

Check for understanding (guide): during share-out, ask the presenting pair: "If I gave you unlimited time to learn Python, which of your three tasks would you tackle first, and why?" A good answer names the most repetitive, rule-based one — not necessarily the most time-consuming one. That is the data-answer (B).

Common student mistakes

Watch for

Naming a task that genuinely requires human judgment at every step (e.g. "deciding which client to prioritize this week") — this is a good moment to contrast with the automatable examples: judgment-heavy tasks are harder to automate, and that distinction is worth surfacing rather than correcting away.

Don't shut down a judgment-heavy example — use it. The contrast between "repetitive + rule-based" and "needs a decision every step" is the sharpest way to make the two automatability properties concrete.
Exercise 5 · 12 min · 0:44–0:56

Draw the Directory Tree

Teaching goal: the reverse direction of Exercise 1 — given paths, reconstruct the tree they imply, including the idea that shared path prefixes mean shared parent folders. Say to the class (verbatim): "Exercise 1 went from a real folder to a written path. Now we go backwards: I give you paths, you draw the tree." Do, live on the board/screen: build the tree incrementally, one path at a time, rather than presenting the finished tree — this is the part that actually teaches the merging logic. First path alone: a straight chain. Second path: ask "where does this branch off from the first one?" (at projects/, since both share home/alice/projects/ and diverge at q1_report vs q2_report). Third path: it shares projects/q1_report/ with the first and diverges at data vs scripts. The shell block on the next slide builds exactly this tree so you can show it settled.

The idea — shared prefix means shared parent

Concept

Given these three paths:

/home/alice/projects/q1_report/data/sales.csv
/home/alice/projects/q2_report/data/sales.csv
/home/alice/projects/q1_report/scripts/summary.py

Wherever two paths share a leading run of segments, they share those folders. All three share /home/alice/projects/; the first and third also share q1_report/. Only where the segments differ does the tree branch.

Build it incrementally on the board: path 1 is a straight chain home → alice → projects → q1_report → data → sales.csv; path 2 branches at projects/; path 3 branches at projects/q1_report/. The core misconception this targets is drawing two separate trees for q1_report and q2_report instead of merging them under projects/.

Projector demo — build the tree from the three paths

cd ~ mkdir -p /home/alice/projects/q1_report/data mkdir -p /home/alice/projects/q1_report/scripts mkdir -p /home/alice/projects/q2_report/data touch /home/alice/projects/q1_report/data/sales.csv touch /home/alice/projects/q1_report/scripts/summary.py touch /home/alice/projects/q2_report/data/sales.csv tree /home/alice/projects

One mkdir -p per directory chain, one touch per file, then tree renders the merged result. The two q1_report paths collapse into one q1_report/ branch with data/ and scripts/ under it; q2_report/ is its own sibling branch. This block leads with a bare cd ~ because it builds a fictional /home/alice tree from scratch — there is no student "setup" location to return to.

Line by line: - cd ~ — start from home (the block builds absolute fictional paths, so where we start doesn't matter). - mkdir -p /home/alice/projects/q1_report/data — -p creates every missing parent in the chain at once. - the other two mkdir -p lines add the scripts and q2_report/data chains; the shared /home/alice/projects prefix is reused, not recreated. - the three touch lines drop the leaf files in. - tree /home/alice/projects — draws the settled tree. The emulator omits the trailing / on folder names that the guide's hand-drawn diagram shows — same structure, illustrative styling.

Exercise 6 · 10 min · 0:56–1:06

RAM vs. Storage Scenarios

Teaching goal: apply the RAM/storage distinction from Exercise 3 to diagnose real (if simplified) technical situations — this is the exercise that reveals whether Exercise 3's vocabulary actually became usable knowledge or stayed inert facts. Say to the class (verbatim): "Three scenarios. For each: is this a RAM problem, a storage problem, or something else? Say your reasoning, not just the label." Do: work through all three together, cold-calling for the reasoning before you confirm.

The distinction

Concept

RAM — fast, temporary. Contents vanish when the power cuts. "Lost my unsaved work" lives here.

Storage — slower, permanent. Files persist with the power off. "File not found" and "slow to read a big file" live here.

And sometimes: neither — no failure happened at all, or the editor already wrote your work to storage on your behalf.

Push for reasoning, not labels. Scenario (c) especially can be RAM or storage or both depending on the machine — press for conditional reasoning ("it depends on whether…") rather than accepting a flat one-word answer.

The three scenarios — verdict + reasoning

(a) Edited a spreadsheet an hour, laptop died, changes goneRAM. The unsaved edits existed only in fast, temporary memory. Never written to storage (never saved), so losing power erased them completely.
(b) Open a CSV, get "file cannot be found"Storage. Either the path is wrong or the file doesn't exist where you're looking — nothing to do with RAM.
(c) Python script is slow processing a 2 GB fileStorage I/O or RAM capacity, or both. Reading 2 GB off disk takes real time; if RAM can't hold the whole file, the OS shuffles data between RAM and storage — much slower than working entirely in RAM.
Cold-call for the reasoning before confirming each verdict. For (b), redirect anyone guessing "RAM" because the error happened "while the program was running": the error itself is about a missing file on disk, a storage concept regardless of when it surfaces. For (c), do not accept a flat "RAM problem" or "storage problem" — press for the conditional "it depends on whether the machine has enough RAM to hold the file."

EXTRA — two more (use if the room is quick, or hold for the wrap-up)

(d) Close editor without saving, reopen later, work is still thereNeither, really — a trick. Most modern editors auto-save to a temp file in storage in the background to survive exactly this. It was never purely a RAM problem — the editor already wrote it to storage for you.
(e) Open a coworker's emailed spreadsheet, edit cells, email it back, never "Save As"Neither — there's no failure here. Naming when a scenario isn't diagnosing a RAM/storage problem is as important a skill as diagnosing the ones that are.
For (d) ask: "was this actually a RAM problem you got lucky on, or never a RAM problem at all?" (Never purely a RAM problem — the editor wrote it to storage on your behalf, which is precisely why it's still there.) For (e), the point is recognizing a no-failure scenario; the round trip never depended on local storage in the failure sense at all.

Knowledge check

In one sentence, the general rule for telling RAM problems and storage problems apart?

"If it's about something being lost when the power went out, it's RAM. If it's about a file not existing or being slow to read, it's storage." When in a program's run an error surfaces tells you nothing about which one it is.

Check for understanding (guide): "Someone tell me, in one sentence, the general rule for telling RAM problems and storage problems apart." (Something like: "If it's about something being lost when the power went out, it's RAM. If it's about a file not existing or being slow to read, it's storage.") That parenthetical is the data-answer (B).

Common student mistakes

Watch for

Labeling scenario (c) as purely a "RAM problem" or purely a "storage problem" instead of recognizing it can be either, or both, depending on the machine — press for the conditional reasoning ("it depends on whether…") rather than accepting a flat one-word answer.

For scenario (b), guessing "RAM" because the error happened "while the program was running" — redirect: the error itself is about a missing file on disk, which is a storage concept regardless of when in the program's execution it surfaces.

Both mistakes come from anchoring on timing ("it happened while running") instead of on what was lost or missing. Keep pulling the reasoning back to the latter.

How Much RAM Does a Real Dataset Need?

Verbatim: "Look up how much RAM Python needs to hold a pandas DataFrame with 1 million rows and 10 float columns, and write 3–4 sentences on why that matters for analysts." If a student asks for the number during class: a pandas float64 DataFrame uses about 8 bytes per cell, so 1,000,000 rows × 10 columns × 8 bytes ≈ 80 MB for the raw data alone — but pandas overhead, indexes, and any object/string columns can push real usage well above that back-of-envelope number, which is exactly the nuance a good Stretch B answer should surface rather than just quoting a single figure.
