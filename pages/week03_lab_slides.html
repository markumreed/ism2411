Learning objectives

By the end of this 75-minute session, students should be able to:

  • Create variables of str, float, int, and bool type and confirm a variable's type with type().
  • Build an f-string that both computes a value inline ({unit_price * quantity}) and formats it for display (:.2f).
  • Convert input()'s string return value to the correct numeric type before doing math with it.
  • Explain why "5" + "3" and 5 + 3 produce different results, and connect that directly to why input() conversion is mandatory, not optional.
  • Use the Python interactive interpreter (the REPL) as a quick scratch space for testing small expressions, separate from running a saved .py file.
The verbs matter. This is the first lab where students write meaningfully structured code themselves — objective 4 (the "5" + "3" reasoning) is the conceptual spine that objective 3 (input() conversion) hangs off of.

Exercise 1 · 8 min · 0:05–0:13

Variables and Types

Teaching goal: every value has a type; type() is how you ask Python what it thinks a value is, and the four types here (str, float, int, bool) are the four students will use constantly all semester. Say to the class: "Four variables, four different types. We're going to ask Python directly what type each one is, rather than just trusting our own guess."

Live-code — Exercise 1

# --- Exercise 1 --- product = "Notebook" unit_price = 4.99 quantity = 12 in_stock = True print(type(product)) print(type(unit_price)) print(type(quantity)) print(type(in_stock))

Type it into the editor unchanged first and Run; then confirm editing a value and re-running still works.

Line by line: - product = "Notebook" — a string (str): text, always wrapped in quotes. The quotes are what make it a string; product = Notebook (no quotes) is a NameError. Worth running that broken version live for 10 seconds — a very common typo. - unit_price = 4.99 — a float: any number with a decimal point, even if that decimal is .00. - quantity = 12 — an int: a whole number, no decimal point at all. 12.0 would be a float — the decimal point is the only thing that matters to Python, not whether the value is whole. - in_stock = True — a bool: exactly True or False, capitalized, no quotes. First time booleans appear this semester as literal values students type — treat it as new. This is not the string "True", it is the keyword True. - print(type(product)) — type() is a built-in that returns a value which prints as <class 'str'>. Say explicitly: that is Python's display format for "this is the string type" — the word class is not something to worry about yet. Don't rabbit-hole.

Expected output

<class 'str'>
<class 'float'>
<class 'int'>
<class 'bool'>
Run it live; confirm every student sees exactly this. Four lines, one per print(type(...)), in the order the variables were defined.

Knowledge check

If I write quantity = "12" instead — with quotes — what does type(quantity) report?

<class 'str'> — the quotes make it text, not a number. This is the exact setup for Exercise 3's input() conversion problem: if you tried to do math with it later, "12" * something would not multiply. Flag that connection now, out loud.

Check for understanding (guide): "what does type(quantity) report, and what would go wrong later if I tried to do math with it?" Answer: <class 'str'> — and this is the exact setup for Exercise 3's input() conversion problem, so flag that connection explicitly now.

Common student mistakes

Watch for

Forgetting quotes around the string value, producing NameError: name 'Notebook' is not defined — a good 10-second live demo.

Writing 12.00 for quantity out of habit (it's dollars-adjacent in their head) and being confused that type() reports float, not int — Python only looks at whether you typed a decimal point, not whether the value "should" be whole.

Writing true (lowercase) instead of True — Python is case-sensitive; true is not a keyword, so this raises NameError just like the unquoted string. Same error type, two totally different mistakes: the category tells you "undefined name," not why.

The lowercase-true and unquoted-string cases both raise NameError — a useful moment to note that an error category names a symptom, not a cause.
Exercise 2 · 8 min · 0:13–0:21

f-string Practice

Teaching goal: an f-string can compute a value inline, not just display an already-computed variable — this is new relative to Module 01's f-string usage (which only displayed pre-computed variables). Say to the class: "So far every f-string you've written has displayed a variable that was already computed on a previous line. Today's version does the math inside the braces, live."

Live-code — Exercise 2

# --- Exercise 2 --- product = "Notebook" unit_price = 4.99 quantity = 12 print(f"{quantity} units of {product} at ${unit_price} each = ${unit_price * quantity:.2f}")

A fresh script run — Exercise 1's print(type(...)) lines are gone, nothing carries over between exercises unless it's re-typed. (Exercise 4 will build a combined script where variables do carry over within one file.)

Walk the string left to right — four separate substitutions: - {quantity} — plain substitution, prints 12. - {product} — plain substitution, prints Notebook. - {unit_price} — plain substitution, prints 4.99. No format spec needed here only because 4.99 already has exactly two decimals — a coincidence of the value, not something to rely on. If unit_price were 5, this would print 5, not 5.00. - {unit_price * quantity:.2f} — the one doing real work: unit_price * quantity is evaluated first (4.99 * 12 = 59.88), then the :.2f format spec is applied to that computed result. The calculation and the formatting are two separate steps in the same braces, in that order. The $ outside the braces is just literal text.

Expected output

12 units of Notebook at $4.99 each = $59.88
Run it live; confirm every student sees exactly this one line. 4.99 * 12 = 59.88, formatted to two decimals by :.2f.

Knowledge check

If I changed unit_price to 5 (no decimal), what does {unit_price * quantity:.2f} print?

60.00 — the format spec does the work of adding the trailing zeros regardless of the input's original precision. (The bare {unit_price} substitution, by contrast, would print 5.)

Check for understanding (guide): walk both substitutions that involve unit_price. {unit_price} alone would print 5; {unit_price * quantity:.2f} would still print 60.00, because :.2f adds the trailing zeros no matter the input precision.

Common student mistakes

Watch for

Putting the format spec on the wrong part of the expression, e.g. {unit_price:.2f * quantity} — a SyntaxError, because the format spec has to come after the complete expression, not in the middle of it. Show this error live; format-spec placement mistakes recur all semester.

Forgetting the $ is a literal character and trying to make it "part of" the number — $ outside the braces is just text.

Read the SyntaxError traceback together — it is a recurring one worth building familiarity with early.
Exercise 3 · 10 min · 0:21–0:31

Input Version — two passes

Teaching goal: convert Exercise 2 from hardcoded values to real user input — and hit the type-conversion requirement head-on, since this is the exercise the reflection questions specifically ask students to reason about. Say to the class: "Same summary line as Exercise 2, but now the values come from whoever runs the script. Watch closely — input() is going to hand us exactly the wrong type for two of these three values, and I want you to predict the failure before we hit it." Two passes: first deliberately WITHOUT conversion (let the room see the failure), then fixed with float() / int().

Pass 1 — broken (no conversion)

# --- Exercise 3 (broken first pass — do not leave this in the final file) --- product = input("Product: ") unit_price = input("Unit price: ") quantity = input("Quantity: ") print(f"{quantity} units of {product} at ${unit_price} each = ${unit_price * quantity:.2f}")

The stdin box is pre-filled with Notebook / 4.99 / 12 — the three input() answers, one per line. Run it: it raises a TypeError.

Explain the error, out loud, slowly: unit_price * quantity is trying to multiply two strings together (both input() results came back as str, unconverted). Python does support * between a string and an int — but that means something completely different from arithmetic (it repeats the string that many times, e.g. "ab" * 3 gives "ababab") — and here Python can't even do that, because both operands are strings, and string-times-string isn't defined at all. Unpacking "can't multiply sequence by non-int of type 'str'" explicitly is the actual teaching moment — it is a genuinely confusing message to a beginner.

Pass 1 — what it raises

Product: Notebook
Unit price: 4.99
Quantity: 12
Traceback (most recent call last):
  File "<exec>", line 5, in <module>
    print(f"{quantity} units of {product} at ${unit_price} each = ${unit_price * quantity:.2f}")
                                                                    ~~~~~~~~~~~^~~~~~~~~~
TypeError: can't multiply sequence by non-int of type 'str'
Verified against CPython 3.12.2 (Pyodide 0.26.4 bundles CPython 3.12, so the traceback body and caret markers match; the file shows as <exec> in Pyodide vs a temp path on a real machine — the load-bearing last line is identical). This IS the exact error from the reflection prompt. Make someone say "TypeError," not just "it breaks."

Pass 2 — fixed (float / int conversion)

# --- Exercise 3 --- product = input("Product: ") unit_price = float(input("Unit price: ")) quantity = int(input("Quantity: ")) print(f"{quantity} units of {product} at ${unit_price} each = ${unit_price * quantity:.2f}")

Same seeded stdin (Notebook / 4.99 / 12). Now it runs.

Line by line, the fix: - unit_price = float(input("Unit price: ")) — input() returns a string; float() wraps that call and converts the result. Same inside-out reading pattern as prior modules. - quantity = int(input("Quantity: ")) — same pattern with int(), since a quantity should be a whole number. - product stays unconverted, deliberately — it's meant to remain text.

Pass 2 — expected output

Product: Notebook
Unit price: 4.99
Quantity: 12
12 units of Notebook at $4.99 each = $59.88
The load-bearing line is the last one — 12 units of Notebook at $4.99 each = $59.88 — which matches the guide's Expected output exactly. The first three lines are the echoed input() prompts + answers from the seeded stdin.

Knowledge check

You forget to convert unit_price to float in Exercise 3. What is the exact error type?

A TypeError, specifically can't multiply sequence by non-int of type 'str' — you can't multiply a string by another string. Make someone say "TypeError," not just "it breaks."

Check for understanding (guide): this is the exact question from tonight's reflection prompt — ask it now, out loud, so students have rehearsed the answer before they see it on the lab page. "What exactly goes wrong, and what's the exact error type, if you forget to convert unit_price to float?" (A TypeError, about not being able to multiply a string by another string.)

Common student mistakes

Watch for

Converting product with str() out of an over-corrected instinct — harmless (it's already a string), but say explicitly: converting a string to a string is a no-op, not an error, just unnecessary.

Converting quantity with float() instead of int() — runs fine, but changes type(quantity) to float, which prints 12.0 instead of 12 in the summary line unless the format spec compensates. Ask the room to predict the output change, live.

Both mistakes run without crashing — good "silent behavior change" examples. Have the room predict before you demo the float()-instead-of-int() swap.
Exercise 4 · 12 min · 0:31–0:43

Multi-Variable Product Card

Teaching goal: combine everything so far — multiple variables, a derived value (margin), and several format specs — into one clean, multi-line report. This is the exercise that most resembles what "real" business scripts look like. Say to the class: "One more variable — unit_cost — and we're computing a derived value, margin, the same formula from the reading. Five lines of output, cleanly aligned."

Live-code — Exercise 4

# --- Exercise 4 --- product = "Notebook" unit_price = 4.99 unit_cost = 3.29 quantity = 12 revenue = unit_price * quantity margin = (unit_price - unit_cost) / unit_price print(f"Product: {product}") print(f"Price: ${unit_price:.2f}") print(f"Qty: {quantity}") print(f"Revenue: ${revenue:.2f}") print(f"Margin: {margin:.1%}")

Labels are padded with extra spaces by hand so the values line up in a column — a manual alignment technique, and a fragile one (a much longer product name breaks it). Better tools exist ({label:<10}) but are out of scope today.

Line by line: - unit_cost = 3.29 — the new variable this exercise introduces. - revenue = unit_price * quantity — same formula pattern, stored in its own variable this time rather than computed inline. Ask: "Why compute this on its own line instead of inline like Exercise 2?" Once a calculation has a name of its own, the code that prints it becomes easier to read — a genuine style upgrade worth naming. - margin = (unit_price - unit_cost) / unit_price — parentheses required for the same order-of-operations reason as always; flag it briefly, don't re-derive. - The five print() lines — currency ${...:.2f}, plain {quantity}, currency again, percentage {margin:.1%}. All four specs have now appeared in this course — say so explicitly.

Expected output

Product:  Notebook
Price:    $4.99
Qty:      12
Revenue:  $59.88
Margin:   34.1%
Run it live; confirm every student sees exactly this. revenue = 4.99 * 12 = 59.88; margin = (4.99 - 3.29) / 4.99 = 0.3407… → 34.1% at one decimal.

Knowledge check

If unit_cost were higher than unit_price — selling at a loss — what prints for margin, and does it crash?

A negative percentage, e.g. -10.0% — no crash, since there's nothing mathematically invalid about a negative margin. Python will happily compute a nonsensical business result without any complaint — the "silent wrong answer" theme again.

Check for understanding (guide): "If unit_cost were higher than unit_price — selling at a loss — what would this script print for margin, and would it crash?" (A negative percentage, e.g. -10.0% — no crash; a good moment to note Python computes nonsensical business results without complaint.)

Common student mistakes

Watch for

Misaligning the manual spacing (extra or missing spaces in the label strings) — cosmetic, not a functional bug, but "does this look like a report" is literally what the exercise tests.

Using unit_price instead of unit_cost in the margin formula by copy-paste habit — produces margin = 0.0 (since unit_price - unit_price is always zero), a "silent wrong answer, and a suspiciously round one." 0.0% margin should visibly look wrong.

The 0.0% case is a good example of a bug that is easy to eyeball once you know to look — encourage a quick "does this number make sense" glance at every output.
Exercise 5 · 12 min · 0:43–0:55

Type Investigation in the REPL

Teaching goal: introduce the Python interactive interpreter (REPL) as a separate tool from running a saved script — a fast scratchpad for testing small expressions — and use it to directly observe the str-vs-int addition distinction that motivates every type-conversion rule so far. Say to the class: "Everything today has been inside a saved file you run with python3 pricer.py. There's a second way to run Python: type python3 with no filename, and you get an interactive prompt where you can type one expression at a time and see the result immediately. This is where you'll quickly test an idea before committing it to a script."

Live-code — Exercise 5 (REPL sequence, wrapped in print() so it runs here)

print(type("12")) print(type(12)) print(type(12.0)) print(type(True)) print("5" + "3") print(5 + 3)

In the real REPL you would type each line bare (no print()) and the interpreter auto-echoes the result — "5" + "3" shows as '53' with quotes, because that's how the REPL marks a string. Here we wrap each in print() so the deck can run it; print() drops the quotes.

Explain each result as it appears: - type("12") → <class 'str'> — the quotes make "12" a string that happens to look like a number; Python treats it purely as text. - type(12) → <class 'int'>, type(12.0) → <class 'float'> — reinforce the decimal-point rule from Exercise 1, now via the REPL. - type(True) → <class 'bool'> — consistent with Exercise 1. - "5" + "3" → 53 (REPL shows '53') — the payoff of the whole exercise. + between two strings means concatenation, not addition. "5" and "3" are text, so + sticks them end to end. - 5 + 3 → 8 — same + symbol, but both operands are int, so it means ordinary arithmetic. Connective idea (say verbatim): "Same symbol, +, two completely different behaviors depending on type. This is exactly why input() results have to be converted before you do math with them — input() always returns a string, so price + tax where both came straight from input() wouldn't add two numbers, it would glue two pieces of text together. And it wouldn't necessarily crash."

Expected output

<class 'str'>
<class 'int'>
<class 'float'>
<class 'bool'>
53
8
Via print(): "5" + "3" shows as 53 (no quotes). In the bare REPL the same line auto-echoes as '53' — the quotes are the REPL telling you "this is a string." Worth a 10-second aside if a sharp student asks why quotes appear in the REPL but not in print() output.

Knowledge check

"5" + 3 — a string plus an int, not two strings — does what?

It raises TypeError: can only concatenate str (not "int") to str. Python refuses to guess which behavior — concatenation or addition — you meant when the types don't match cleanly. That refusal is genuinely reassuring: it means Python won't silently do the wrong thing here.

Check for understanding (guide): "Predict, before I run it: what does "5" + 3 — a string plus an int — do?" (Raises TypeError: can only concatenate str (not "int") to str — demonstrate live if time allows; a natural bridge into "Python refuses to guess which behavior you meant when the types don't match cleanly.")

Common student mistakes

Watch for

Typing exit() or closing the terminal window instead of using Ctrl+D (Mac/Linux) or Ctrl+Z then Enter (Windows) to leave the REPL — not wrong, just slower; mention the shortcut once.

Confusion about why the REPL echoes back a value (like '53') for a bare expression but does nothing extra for a bare print(...) — the REPL auto-displays the result of the last expression typed, a REPL-only convenience. A saved script never does this, which is precisely why print() is required in every script exercise all semester.

The auto-echo vs explicit-print() distinction is the reason scripts always need print() — worth making explicit here.
Stretch A · 15 min · 0:55–1:10

Three-Product Comparison

Teaching goal: scale Exercise 4's single product card to three products using parallel variable naming, and use comparison operators to pick a winner — direct rehearsal for the "many records" processing that loops (a later module) will handle more elegantly. Say to the class: "Three products, three full sets of variables, three margins — and a final line declaring the winner. This previews a real pain point: right now, with no loops yet, three products means typing almost the same code three times. Notice that discomfort — it's setting up why we'll want a better tool for this soon."

Live-code — Stretch A (loop version)

# --- Stretch A --- product1, price1, cost1, qty1 = "Notebook", 4.99, 3.29, 12 product2, price2, cost2, qty2 = "Pen", 1.99, 0.85, 50 product3, price3, cost3, qty3 = "Stapler", 12.49, 7.10, 5 margin1 = (price1 - cost1) / price1 margin2 = (price2 - cost2) / price2 margin3 = (price3 - cost3) / price3 for name, price, qty, margin in [ (product1, price1, qty1, margin1), (product2, price2, qty2, margin2), (product3, price3, qty3, margin3), ]: print(f"Product: {name} | Price: ${price:.2f} | Qty: {qty} | " f"Revenue: ${price * qty:.2f} | Margin: {margin:.1%}") best_margin, best_product = max([(margin1, product1), (margin2, product2), (margin3, product3)]) print(f"Highest margin: {best_product} at {best_margin:.1%}")

If your section hasn't covered for loops yet, replace the loop with three explicit, separately-typed print() calls (one per product) — the appendix answer key shows both versions, and both give the same first three output lines.

Line by line: - The three productN, priceN, costN, qtyN = ... lines — tuple unpacking, scaled to three parallel sets. Numbered variable names like this are a known anti-pattern — the exercise is teaching students to feel that pain, not endorsing it. Honest answer to "isn't there a better way": "yes, a list of dictionaries or a loop-friendly structure — that's a later module; today is intentionally the 'hard way' so the better way lands harder." - The for loop over a list of tuples is one legitimate way to avoid three near-identical print() calls. If for loops aren't in scope for your section, use three explicit print() calls instead so the loop syntax doesn't introduce an unannounced concept. - max([(margin1, product1), ...]) — max() on a list of tuples compares tuples element by element, so it compares the margins first (margin is listed first in each tuple) and only looks at the product name to break ties. Tuple comparison does the comparison logic for you. Check for understanding (guide): "If I added a fourth product, what has to change?" (Every numbered-variable line needs a new set — product4, price4, cost4, qty4 — and the loop's list or the manual print calls need a fourth entry. Get someone to say out loud that this doesn't scale — that's the intended discomfort.)

Expected output

Product: Notebook | Price: $4.99 | Qty: 12 | Revenue: $59.88 | Margin: 34.1%
Product: Pen | Price: $1.99 | Qty: 50 | Revenue: $99.50 | Margin: 57.3%
Product: Stapler | Price: $12.49 | Qty: 5 | Revenue: $62.45 | Margin: 43.2%
Highest margin: Pen at 57.3%
Four lines: one per product, then the winner. Pen has the highest margin (57.3%) even though it has the lowest unit price — a nice "margin and price are different questions" aside. Common mistake to watch for: mixing up which numbered variable belongs to which product mid-script (e.g. using cost2 in a formula meant for product 3) — the classic consequence of the numbered-variable anti-pattern.
Stretch B · as time allows

Format Spec Exploration

Frame it as a quick, verbal walkthrough rather than a full live-coded block if time is short — designed as REPL exploration, not a script. If time is genuinely tight, this closing line alone is worth saying: "Everything in that : after the value in an f-string is its own small formatting language — you've now seen currency, percentages, thousands separators, zero-padding, and alignment. That's most of what you'll need all semester."

Live-code — Stretch B (format specs)

print(f"{1234567:.2f}") print(f"{1234567:,.0f}") print(f"{0.3456:.1%}") print(f"{42:05d}") print(f"{'hello':>20}")

In the REPL each bare f-string auto-echoes with surrounding quotes; via print() here you see the string contents directly.

One sentence each, said out loud: - .2f forces two decimals even on a whole number. - ,.0f adds thousands separators with zero decimals. - .1% multiplies by 100 and appends a percent sign, one decimal digit. - 05d pads an integer with leading zeros to a total width of 5 characters (order numbers, zip codes). - >20 right-aligns text within a 20-character-wide field (the "columns that line up" problem Exercise 4's manual spacing was working around by hand).

Expected output

1234567.00
1,234,567
34.6%
00042
               hello
Line 5 is hello right-aligned in a 20-char field — 15 leading spaces then the 5 letters. In the bare REPL these show as '1234567.00', '1,234,567', '34.6%', '00042', ' hello' (with quotes).
