Exercise 1 · 5 min · 0:05–0:10

Revenue

Teaching goal: multiplication as the business operation "price times quantity," and the first f-string format spec of the semester: thousands separator + fixed decimals. Say to the class (verbatim): "Revenue is the simplest formula in the whole lab — price times quantity — but the output formatting is the actual skill we're practicing. $600 and $600.00 mean the same number to Python, but only one of them looks like something a manager would accept in a report."

Live-code — Exercise 1

# --- Exercise 1 --- price = 50 quantity = 12 revenue = price * quantity print(f"Revenue: ${revenue:,.2f}")

Type it unchanged and Run. Expected: Revenue: $600.00.

Line-by-line: - price = 50 — an integer variable. No dollar sign, no comma, no quotes — just the raw number. price = "$50" would make this a string, and "$50" * 12 would repeat the text, not multiply. Worth a 15-second aside. - quantity = 12 — likewise a plain integer. - revenue = price * quantity — * is multiplication; both operands are int, so revenue is also an int (600), not a float yet. - print(f"Revenue: ${revenue:,.2f}") — slow down here. The f before the quote makes this an f-string: anything in { } is Python code, evaluated and substituted. The literal $ is just a character. Inside the braces, revenue is the value; everything after : is the format spec. , inserts a thousands separator (1200 → 1,200) — not needed for 600 here, but essential in Exercise 6. .2f means "fixed-point, 2 digits after the decimal" — turns the integer 600 into the display string 600.00. This changes only the display, not the stored value. Common mistakes: forgetting the f (braces print literally — most common error in the room, walk by and check); putting the format spec outside the braces (f"...${revenue}:,.2f"); writing .2f, instead of ,.2f → ValueError: Invalid format specifier (next slide shows it). Check for understanding (guide): "If I change quantity to 12.5, does this line still work, and does the output still make sense?" Answer: Yes — revenue becomes a float, ,.2f still formats it correctly. This previews that ,.2f works on both ints and floats, which matters in Exercise 6.

Expected output

Revenue: $600.00
Run it live; confirm every student sees exactly this. Matches the guide's "Run it. Expected output" for Exercise 1.

Deliberately broken — comma in the wrong place

# --- Exercise 1 (deliberately broken: comma misplaced in the format spec) --- price = 50 quantity = 12 revenue = price * quantity print(f"Revenue: ${revenue:.2f,}")

Students who write .2f, instead of ,.2f get a ValueError. Run it — read the message aloud once.

Teaching goal: the format spec has a fixed grammar; the separator comes before the precision, not after. The error message actually says Invalid format specifier, which is worth reading aloud once so students recognize it later. Line-by-line: identical to the working version except the format spec is :.2f, — a trailing comma Python cannot parse. Common mistakes: this is the mistake — confusing ,.2f order. Show the traceback, then fix it back to ,.2f and move on. The file path shows as <exec> in Pyodide vs a temp path under CPython — not load-bearing. The load-bearing last line is ValueError: Invalid format specifier '.2f,' for object of type 'int'.

Exercise 2 · 5 min · 0:10–0:15

Margin

Teaching goal: true division (/) always returns a float, and the .1% format spec — the first time students see Python multiply a decimal by 100 and add a % sign automatically. Say to the class (verbatim): "Margin is the percentage of the price that's profit. The formula is (price - cost) / price. Watch what happens with the formatting here — we are not going to multiply by 100 ourselves."

Live-code — Exercise 2

# --- Exercise 2 --- cost = 32 price = 50 margin = (price - cost) / price print(f"Margin: {margin:.1%}")

Expected: Margin: 36.0%. Note the parentheses around price - cost are required, not stylistic.

Line-by-line: - cost = 32, price = 50 — reusing price here shadows the value from Exercise 1. Variables are not scoped per-exercise; it's fine here because it's the same value, but flag that Exercise 3 renames to price_a / price_b to avoid this kind of collision. - margin = (price - cost) / price — the parentheses are required. price - cost / price would divide cost by price first (division binds tighter than subtraction) and then subtract — a completely different, wrong number. This is the first live preview of the operator-precedence trap; flag it now so it's not a surprise later. - / is true division — always returns a float, even when the answer comes out evenly (10 / 2 is 5.0). Contrast verbally with //, coming in Exercise 5. - margin is 0.36 — a decimal fraction, not "36". - f"Margin: {margin:.1%}" — the % format type multiplies by 100 and appends a literal %. .1 means one digit after the decimal in the percentage. So 0.36 becomes 36.0%. Common mistakes: manually multiplying by 100 first (... / price * 100) and then using .1%, which double-multiplies → 3600.0%. Extremely common — make the student explain out loud why the number is 100x too big. Also omitting the parentheses around price - cost. Check for understanding (guide): "What data type is margin right now — before it's ever printed?" Answer: a float, 0.36. The % in the f-string changes display, not the stored type.

Expected output

Margin: 36.0%
Run it live. (50 - 32) / 50 = 0.36; .1% renders that as 36.0%. Matches the guide's "Run it. Expected output" for Exercise 2.

A float, 0.36. The % in the f-string changes display, not the stored type — reinforce this distinction, it recurs in Exercise 6.

Check for understanding (guide, verbatim parenthetical): "(A float, 0.36. The % in the f-string changes display, not the stored type — reinforce this distinction, it recurs in Exercise 6.)"

Common student mistakes

Watch for

Manually multiplying by 100 first (margin = (price - cost) / price * 100) and then using .1% — this double-multiplies and gives 3600.0%. Very common. Don't just correct it; ask the student to explain out loud why the number is 100x too big — "because % already multiplies by 100" is what makes it stick.

Exercise 3 · 7 min · 0:15–0:22

Two Products

Teaching goal: comparison operators produce a bool, and a bool is a real, printable value — not a string, not a special case. Say to the class (verbatim): "Now we compare two products by margin. Notice I'm renaming variables this time — price_a, cost_a, price_b, cost_b — because we just saw what happens when you reuse a bare price for two different things. This exercise also introduces the bool type: True and False, capitalized, no quotes."

Live-code — Exercise 3

# --- Exercise 3 --- price_a, cost_a = 50, 32 price_b, cost_b = 80, 60 margin_a = (price_a - cost_a) / price_a margin_b = (price_b - cost_b) / price_b product_a_wins = margin_a > margin_b print(f"Product A margin: {margin_a:.1%}") print(f"Product B margin: {margin_b:.1%}") print(f"Product A wins: {product_a_wins}")

Ask the room to predict both margins before running — 36.0% and 25.0%. Product B has a lower margin despite a higher price.

Line-by-line: - price_a, cost_a = 50, 32 — tuple unpacking: one line assigns two variables, left to right. Optional shorthand for two separate lines — either style is fine. - margin_a = (price_a - cost_a) / price_a and the matching margin_b line — identical formula from Exercise 2, applied to each product. Predict before running: 36.0% and 25.0%. Higher price does not automatically mean higher margin (10-second business aside). - product_a_wins = margin_a > margin_b — > is a comparison operator. This line does not print and does not branch — it evaluates margin_a > margin_b to True or False and stores that value. A comparison is an expression that produces a value, exactly like 2 + 2 produces 4. - print(f"Product A wins: {product_a_wins}") — product_a_wins is a bool; f-strings print booleans as the literal words True / False (capital, no quotes). True is not the string "True" — if product_a_wins == "True": would silently never match. Worth stating now even though if is Module 05. Common mistakes: writing = instead of ==, or an assignment chain like product_a_wins = margin_a = margin_b which silently overwrites both margins. Distinguish = (assignment, "put this value in this box") from > < == (comparison, "ask a true/false question"). Check for understanding (guide): "If Product B's margin had been higher than Product A's, what would product_a_wins print?" Answer: False — the variable name doesn't change what's stored in it; product_a_wins is just a label, it will happily hold False.

Expected output

Product A margin: 36.0%
Product B margin: 25.0%
Product A wins: True
Run it live. margin_a = 0.36, margin_b = 0.25, 0.36 > 0.25 is True. Matches the guide's "Run it. Expected output" for Exercise 3.

Knowledge check

If Product B's margin had been higher than Product A's, what would product_a_wins print?

False — the variable name doesn't change what's stored in it; product_a_wins is just a label, it will happily hold False.

Check for understanding (guide, verbatim parenthetical): "(False — make someone say it out loud, and make someone else explain that the variable name doesn't change what's stored in it; product_a_wins is just a label, it will happily hold False.)"

Common student mistakes

Watch for

Confusing = with a comparison. They haven't hit == yet (that's Exercise 4), but if a student writes product_a_wins = margin_a = margin_b out of confusion, catch it — that's an assignment chain, not a comparison, and it silently overwrites margin_a and margin_b both to whatever margin_b was.

Good moment to distinguish = (assignment — "put this value in this box") from > < == (comparison — "ask a true/false question").

Exercise 4 · 8 min · 0:22–0:30

Logical Combo

Teaching goal: combining two boolean conditions with and, and observing how changing one input changes the combined result. Say to the class (verbatim): "A 'premium' product needs to satisfy two conditions at once: price over 100 AND margin over 30%. This is where and comes in — it's not addition, it's a logical operator that only returns True when both sides are True."

The idea — the and truth table

Say it once, explicitly

True and True → True. Every other combination — True and False, False and True, False and False → False. Both sides must be true.

Python evaluates price > 100 and margin > 0.3 in three explicit steps: first price > 100 on its own, then margin > 0.3 on its own, and only then does and combine the two booleans.

Students commonly try to read price > 100 and margin > 0.3 as one big arithmetic-style expression; walk it in three explicit steps on the board/screen. This card is the guide's "and truth table" plus its "read this out loud exactly as Python evaluates it" paragraph.

Pass 1 — both conditions met

# --- Exercise 4 --- price = 120 margin = 0.35 is_premium = price > 100 and margin > 0.3 print(f"is_premium = {is_premium}")

Expected: is_premium = True. 120 > 100 → True; 0.35 > 0.3 → True; True and True → True.

Line-by-line: - price = 120, margin = 0.35 — margin is entered directly as a decimal here (not computed), since this exercise isolates the logic, not the formula. - is_premium = price > 100 and margin > 0.3 — first price > 100 (120 > 100 → True), then margin > 0.3 (0.35 > 0.3 → True), then and combines them (True and True → True). Common mistakes: writing margin > 30 (forgetting margin is a decimal, not a whole-number percentage) — runs without error, always evaluates unexpectedly. A "silent wrong answer" bug. Also confusing and with & (bitwise, not logical) — one sentence: "we're not using that operator today."

Pass 1 — expected output

is_premium = True
Matches the guide's "Run it. Expected output" for Exercise 4's first values.

Pass 2 — change the values so exactly one condition is met

# --- Exercise 4 (one condition met, not both) --- price = 120 margin = 0.20 is_premium = price > 100 and margin > 0.3 print(f"is_premium = {is_premium}")

Output is is_premium = False, even though price > 100 alone is True. This is the entire point of the exercise.

Say explicitly: "One true condition is not enough for and. Both have to be true." price > 100 is True, but margin > 0.3 is now False (0.20 > 0.3 is false), so True and False → False. Next slide shows the reverse case for the same reason from the other side.

Pass 2 — expected output

is_premium = False
One true condition is not enough for and. Verified against CPython 3.12.2.

Pass 3 — the reverse: price fails, margin passes

# --- Exercise 4 (the other side: price fails, margin passes) --- price = 80 margin = 0.35 is_premium = price > 100 and margin > 0.3 print(f"is_premium = {is_premium}")

Also False — for the same reason from the other side: False and True → False.

The guide: "Then try the reverse (price = 80, margin = 0.35) and get False again, for the same reason from the other side." 80 > 100 is False; False and True → False.

Pass 3 — expected output

is_premium = False
Verified against CPython 3.12.2. and needs both sides true; failing either side, from either direction, yields False.

I want to check if a product is premium OR on clearance — would I use and here?

Exercise 5 · 10 min · 0:30–0:40

Common-Mistake Check: /, //, %

Teaching goal: this is the highest-leverage exercise in the lab. Students must be able to distinguish true division, floor division, and modulo — this distinction underpins Exercise 7 and half of next semester's logic. Say to the class (verbatim): "Before we run anything — everyone write down, on paper or in a comment, your prediction for 17 / 5, 17 // 5, and 17 % 5. I will cold-call three of you before we run this." Do this as a genuine predict-then-verify exercise — do not type the code until predictions are collected. Common wrong predictions: 17 // 5 predicted as 3.4 (confusing it with /); 17 % 5 predicted as some kind of percentage (% here is the modulo operator, unrelated to the .1% format spec from Exercise 2 — two completely different uses of the same character).

Predict — before running

Write down your prediction for each: 17 / 5, 17 // 5, 17 % 5. The instructor will cold-call three students before the code is typed.

17 / 5  -> 3.4   true division: divide normally, always returns a float
17 // 5 -> 3     floor division: divide, then round DOWN to a whole number
17 % 5  -> 2     modulo: the remainder left after floor division (17 = 5*3 + 2)
Reveal only after predictions are collected. Common wrong predictions: 17 // 5 as 3.4; 17 % 5 as a percentage. The identity (a // b) * b + (a % b) always reconstructs a — write it on the board, it is the single sentence that makes Exercise 7 make sense.

Live-code — Exercise 5

# --- Exercise 5 --- print(17 / 5) # true division print(17 // 5) # floor division print(17 % 5) # modulo (remainder)

Expected output: 3.4, then 3, then 2. Then have each student write one sentence per operator explaining what it does and when they'd use it in a business calculation (2 minutes of quiet writing — it's built into the 10-minute budget).

Line-by-line: - 17 / 5 — true division, always returns a float: 3.4. "What a calculator gives you." - 17 // 5 — floor division: divide, then round down to the nearest whole number, discarding the fractional part entirely (toward negative infinity, not toward zero). Result: 3. Two positive ints → an int; 17.0 // 5 is 3.0. - 17 % 5 — modulo: the remainder after floor division. 17 = 5 × 3 + 2, so the remainder is 2. // and % are a matched pair: (a // b) * b + (a % b) always reconstructs a. Common mistakes: assuming // rounds to the nearest integer rather than always down (-7 // 2 is -4, not -3 — optional aside). Confusing % the operator with % in a format spec — same character, two unrelated meanings depending on context. Check for understanding (guide): "If I have 50 items and box size 8, what does 50 // 8 give me, and what does 50 % 8 give me — without running it?" Answer: 6 full boxes, 2 left over. Hand-verify: 8 × 6 = 48, 50 − 48 = 2. This is exactly what Exercise 7 automates.

Expected output

3.4
3
2
Run it live; confirm every student sees exactly this. Matches the guide's "Run it. Expected output" for Exercise 5. Note 3.4 is a float (true division), 3 and 2 are ints.

Knowledge check

I have 50 items and a box size of 8. Without running it — what does 50 // 8 give, and what does 50 % 8 give?

6 full boxes, 2 left over. Verify by hand: 8 × 6 = 48, 50 − 48 = 2. This hand-verification is exactly what Exercise 7 automates.

Check for understanding (guide, verbatim parenthetical): "(6 full boxes, 2 left over. Have someone verify by hand: 8 × 6 = 48, 50 − 48 = 2. This hand-verification is exactly what Exercise 7 automates.)"

Common student mistakes

Watch for

Assuming // rounds to the nearest integer rather than always down. If time allows: -7 // 2 is -4, not -3 — floor division rounds toward negative infinity, not toward zero. Optional; skip it if you're behind.

Exercise 6 · 15 min · 0:40–0:55

Full Pricing Calculator

Teaching goal: collecting multiple inputs with input(), converting text to numbers with float(), and chaining several of today's formulas into one coherent report. This is the exercise students will spend the most time on independently — go a little slower and leave room for the room to type along in real time. Say to the class (verbatim): "Everything up to now used values we typed directly into the script. Real tools ask the user for values. input() always returns a string — even if someone types 50 — so every numeric input has to be explicitly converted, or your very first calculation will crash." Build it in three passes — first just the inputs, then the calculations, then the formatted report. Do not type the whole block at once.

Pass 1 — collect inputs (with a debug print)

# --- Exercise 6 (Pass 1 — collect inputs, debug-print to confirm) --- product_name = input("Product name: ") retail_price = float(input("Retail price: ")) unit_cost = float(input("Unit cost: ")) quantity_sold = int(input("Quantity sold: ")) discount_percent = float(input("Discount percent (e.g. 10 for 10%): ")) print(product_name, retail_price, unit_cost, quantity_sold, discount_percent)

Stdin seeded with Wireless Mouse / 29.99 / 11.50 / 340 / 15. The last print is a temporary debug line — remove it before Pass 2.

Line-by-line: - product_name = input("Product name: ") — input() displays the prompt, pauses, and returns whatever the user typed as a string, always — even "340" comes back as text. product_name genuinely is a string, so no conversion needed here. - retail_price = float(input("Retail price: ")) — read inside-out: input(...) runs first and returns a string ("29.99"), then float(...) converts it. Function composition — one function's return value fed directly into another. - unit_cost = float(...) — same pattern. - quantity_sold = int(input(...)) — uses int(), not float(), because a quantity should be a whole number. If a student types 340.5 here, int("340.5") raises a ValueError — next slide runs that live. - discount_percent = float(...) — collected as a whole number like 15, not 0.15; the conversion to a decimal fraction happens in Pass 2. Common mistakes: forgetting float()/int() around input() entirely — walk the room during Pass 1 for this.

Pass 1 — expected output

Product name: Wireless Mouse
Retail price: 29.99
Unit cost: 11.50
Quantity sold: 340
Discount percent (e.g. 10 for 10%): 15
Wireless Mouse 29.99 11.5 340 15.0

Under a headless python3 pipe the five prompts print concatenated on one line before the debug line — not load-bearing. The load-bearing line is the last one: Wireless Mouse 29.99 11.5 340 15.0 — note float("11.50") prints as 11.5 and float("15") as 15.0. Remove this debug print before Pass 2.

Pass 2 — compute (shown for reference — needs Pass 1's inputs to run)

discount_decimal = discount_percent / 100
revenue = retail_price * quantity_sold
discounted_revenue = revenue * (1 - discount_decimal)
gross_margin = (retail_price - unit_cost) / retail_price
net_profit = discounted_revenue - (unit_cost * quantity_sold)

This block only makes sense on top of Pass 1's variables — the runnable full script is on the next slide.

Line-by-line: - discount_decimal = discount_percent / 100 — the exact conversion flagged as missing in Pass 1: 15 becomes 0.15. Call back to the Exercise 4 mistake pattern and to the reflection question, which asks students to describe exactly this bug. - revenue = retail_price * quantity_sold — same formula as Exercise 1, now with live user input. - discounted_revenue = revenue * (1 - discount_decimal) — if the discount is 15%, the customer pays 85%, so multiply revenue by (1 - 0.15) = 0.85. The parentheses around 1 - discount_decimal are required — without them, order of operations multiplies discount_decimal by revenue first, then subtracts from 1: a nonsense number. - gross_margin = (retail_price - unit_cost) / retail_price — identical formula to Exercise 2, at the per-unit level (margin doesn't depend on quantity). - net_profit = discounted_revenue - (unit_cost * quantity_sold) — total cost of goods sold is unit_cost * quantity_sold; net profit is what's left of discounted revenue after covering it. The parentheses here aren't strictly required (* binds tighter than -) but include them anyway — explicit parentheses that aren't strictly necessary are still good practice, they make the formula readable without recalling precedence rules. A style point, not a correctness one.

# --- Exercise 7 --- items_ordered = int(input("Items ordered: ")) box_size = 24 full_boxes = items_ordered // box_size loose_items = items_ordered % box_size exact_fit = loose_items == 0 print(f"Full boxes: {full_boxes}") print(f"Loose items: {loose_items}") print(f"Exact fit: {exact_fit}")
