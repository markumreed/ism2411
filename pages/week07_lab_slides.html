Learning objectives

By the end of this 75-minute session, students should be able to:

  • Define a function with def, including parameters and a return statement, and explain the difference between a function returning a value and merely printing one.
  • Call one function from inside another (composition), and trace the flow of a value through a short chain of function calls.
  • Use a for loop to call the same function repeatedly over a list of inputs.
  • Explain local vs. global scope: why a variable assigned inside a function doesn't affect a same-named variable outside it.
  • Apply a disciplined, four-step debugging protocol — solo trace, narrowly-scoped AI question, self-written fix, debrief — before defaulting to "ask AI to fix it."

Exercise 1 · 6 min · 0:04–0:10

calculate_tax

Teaching goal: the absolute minimum function — def, parameters, return — and the crucial distinction between a function that returns a value and one that merely prints. Say to the class (verbatim): "Simplest possible function: takes a price and a rate, returns the tax. One line of logic — but the syntax around that one line is entirely new today."

Live-code — Exercise 1

# --- Exercise 1 --- def calculate_tax(price, rate): return price * rate print(f"Tax on $100 at 7%: ${calculate_tax(100, 0.07):.2f}") print(f"Tax on $250 at 8%: ${calculate_tax(250, 0.08):.2f}")

Type it unchanged and Run. The function never calls print() itself — it hands a number back, and the caller (the print(f"...") line) decides to display it.

Line-by-line: - def calculate_tax(price, rate): — def begins a function definition. calculate_tax is the name you're choosing — same naming rules as variables. (price, rate) are parameters: named placeholders for values the function expects to receive when called; they don't hold any actual value yet, they're just names the function body will refer to. The colon and the indented block below it work exactly like if and for — indentation marks what's "inside" the function. - return price * rate — this is the line that makes it a function that produces a usable value, rather than one that just prints. return hands a value back to whatever called the function, and immediately ends the function's execution — say explicitly: nothing runs after a return statement inside the same function call. - calculate_tax(100, 0.07) — a call: the function actually runs now, with price bound to 100 and rate bound to 0.07 for the duration of this call only. The returned value (7.0) is what this expression evaluates to — it slots directly into the f-string's {...}, formatted with :.2f. - The distinction to land explicitly: calculate_tax never calls print() itself — it hands a number back. It's the caller that decides to display it. A function that returns a value can be reused in a calculation (like Exercise 3 is about to do); a function that only prints cannot — you can't do math with what print() "gives back" (technically None). Common mistakes: writing print(price * rate) inside the function instead of return price * rate — runs without error, looks right if you run it once, but hands back None to any code trying to use the result (demonstrated on the next slides); forgetting the parentheses when calling (writing calculate_tax instead of calculate_tax(100, 0.07)) — no error, but refers to the function object itself and prints <function calculate_tax at 0x...>. Check for understanding (guide, verbatim parenthetical): "If I call calculate_tax(250, 0.08) five times in a row in my script, how many times do I have to write the formula price * rate? (Once — inside the function definition. This is the entire value proposition of a function, worth stating explicitly as the payoff for the new syntax overhead.)"

Deliberately broken — print inside the function instead of return

# --- Exercise 1 (BROKEN: print instead of return) --- def calculate_tax(price, rate): print(price * rate) print(calculate_tax(100, 0.07) + 5)

Replace return with print, then try to do math with the result: calculate_tax(100, 0.07) + 5. It prints the tax once, then raises a TypeError — a preview of exactly the kind of bug the return-vs-print distinction prevents.

Teaching goal: show why return matters by breaking it — a function that only prints hands back None, which is unusable in any further calculation. Line-by-line: calculate_tax now prints price * rate and returns nothing (implicitly None). So calculate_tax(100, 0.07) displays 7.000000000000001 as a side effect but the expression itself evaluates to None; None + 5 is undefined, so Python raises TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'. Common mistakes: this is the mistake the guide flags — worth showing live for 10 seconds so students see the resulting TypeError before it's abstract. The stray 7.000000000000001 above the traceback is float precision (100 * 0.07 can't be represented exactly in binary), not part of the bug.

Exercise 2 · 8 min · 0:10–0:18

apply_discount

Teaching goal: a function whose body contains a full if/elif/else chain (Module 05's logic, now packaged) — confirms functions can contain any code students already know how to write, not just a single expression. Say to the class (verbatim): "Functions aren't limited to one line. This one has a whole discount-tier decision inside it — the exact if/elif/else shape from Module 05, just packaged with a name and parameters now."

Live-code — Exercise 2

# --- Exercise 2 --- def apply_discount(price, tier): if tier == "gold": discount = 0.15 elif tier == "silver": discount = 0.10 elif tier == "bronze": discount = 0.05 else: discount = 0 return price * (1 - discount) for tier in ["gold", "silver", "bronze", "none"]: print(f"{tier}: ${apply_discount(200, tier):.2f}")

All four branches lead to the same single return line, placed after the whole if/elif/else chain at the function's top indentation level — not one return per branch.

Line-by-line: - The if/elif/else block is entirely inside the function body — every line indented one level under def, and the if/elif bodies indented a second level under that, exactly the nested-indentation pattern from Module 06's Exercise 4. - return price * (1 - discount) — placed after the entire chain, at the function's top indentation level (not inside any branch): all four branches lead to the same single return line. Ask the room: "would it work just as well to put return price * (1 - discount) inside each of the four branches instead, four separate times?" (Yes, functionally — but one return after the decision is made is less repetitive and keeps the "what does this function give back" logic in one place, a real readability win as functions grow.) - for tier in [...]: calls apply_discount four times, once per tier name — direct rehearsal of Module 06's "loop + function-shaped logic" pattern, now with an actual function being called. Common mistakes: indenting return one level too deep (inside the else block only) — every tier except "none" then returns None; misspelling a tier string (e.g. "Gold") — case-sensitive comparison silently falls through to else and returns the undiscounted price. Check for understanding (guide, verbatim parenthetical): "What does apply_discount(200, "platinum") return — a tier that doesn't exist in the function at all? ($200.00 — the full, undiscounted price, since "platinum" matches none of the if/elif conditions and falls through to else. No error, no warning — worth stating explicitly as a real design tradeoff.)"

Compose Them

Teaching goal: call one function from inside the body of another — composition — and see directly why Exercise 1's choice of return over print was essential to making this possible at all. Say to the class (verbatim): "This is the payoff for using return instead of print in both functions so far — we're about to feed one function's output directly into another, which is only possible because each one hands back a usable value." Live-code in two stages: first manually, then wrapped in a third function.

The idea — one function's return value becomes another's input

Say it once, explicitly

Composition is genuinely one of the more abstract ideas in the whole course so far. final_price doesn't duplicate any discount or tax logic itself — it delegates both jobs to apply_discount and calculate_tax and combines the results.

Tax is computed on the discounted price ($170.00), not the original $200 — that's the actual business logic being modeled, not just a syntax point. It's fine if the room takes a moment to track all three functions at once.

This card is the guide's framing for Exercise 3's "Line-by-line explanation" — composition made explicit, and the note that if this feels like a lot of layers, that's worth naming out loud. Stage 1 does the composition by hand with intermediate variables; stage 2 wraps the exact same two calls inside a third function's definition.

Live-code — Exercise 3 (stage 1: manual composition)

# --- Exercise 3 (stage 1: manual composition) --- def calculate_tax(price, rate): return price * rate def apply_discount(price, tier): if tier == "gold": discount = 0.15 elif tier == "silver": discount = 0.10 elif tier == "bronze": discount = 0.05 else: discount = 0 return price * (1 - discount) after_discount = apply_discount(200, "gold") after_tax = after_discount + calculate_tax(after_discount, 0.07) print(f"After gold discount: ${after_discount:.2f}") print(f"After tax: ${after_tax:.2f}")

This block re-defines calculate_tax and apply_discount because each runnable block runs in its own fresh namespace. In the real functions.py they were typed once, in Exercises 1–2.

Line-by-line: - after_discount = apply_discount(200, "gold") — Exercise 2's function, called and its return value stored in a variable, exactly like calling any built-in function (float(), type()) — there's no special syntax difference between calling a function you wrote and one Python provides. - calculate_tax(after_discount, 0.07) — note this passes after_discount (the discounted price, $170.00), not the original $200 — tax is computed on the discounted amount, which is worth stating as the actual business logic being modeled, not just a syntax point. Common mistakes: passing the original price (200) instead of the discounted price into calculate_tax — computes tax on the wrong base, $14.00 instead of $11.90, final total $184.00 instead of $181.90 (demonstrated on the next slides). Check for understanding is on slide 34.

Live-code — Exercise 3 (stage 2: wrap it in a third function)

# --- Exercise 3 (stage 2: wrap it in a third function) --- def calculate_tax(price, rate): return price * rate def apply_discount(price, tier): if tier == "gold": discount = 0.15 elif tier == "silver": discount = 0.10 elif tier == "bronze": discount = 0.05 else: discount = 0 return price * (1 - discount) def final_price(price, tier, tax_rate): discounted = apply_discount(price, tier) return discounted + calculate_tax(discounted, tax_rate) print(f'final_price(200, "gold", 0.07) = ${final_price(200, "gold", 0.07):.2f}')

A new function whose entire body is two calls to the other two functions, chained. One function's return value (discounted) becomes the input to a second function call, inside a third function's own definition.

Line-by-line: - def final_price(price, tier, tax_rate): — a new function whose entire body is two calls to the other two functions, chained together. This is composition made explicit: final_price doesn't duplicate any discount or tax logic itself — it delegates both jobs out and combines the results. - discounted = apply_discount(price, tier) then return discounted + calculate_tax(discounted, tax_rate) — one function's return value (discounted) becomes the input to a second function call, inside a third function's own definition. If this feels like a lot of layers, that's worth naming explicitly: composition is genuinely one of the more abstract ideas in the whole course so far. Common mistakes: defining final_price but forgetting it depends on apply_discount and calculate_tax already being defined earlier in the file — reordering the script so final_price is called before those two are defined gives a NameError. Python reads top to bottom; "define before you call" is the practical rule for this lab's straightforward script. Check for understanding is on slide 34.

Scope Experiment

Teaching goal: local vs. global scope — a genuinely surprising result the first time you see it, and essential for understanding why functions don't accidentally corrupt variables outside themselves. Say to the class (verbatim): "Predict the output of this before I run it — write down your three guesses." Live-code it only after collecting predictions. The idea — two xs that briefly exist at once

Say this twice, differently

Assigning to x inside double_it() creates a brand new, separate local variable, also named x, that exists only inside this function call and only for its duration. It does not modify the global x.

"There are now two xs that both exist briefly at the same time — a global one worth 100, and a local one worth 999 — and the function has no way to see or touch the global one once it's created its own local x." When the function returns, the local x is destroyed; the global x was never touched.

This card is the guide's "Line-by-line explanation, in the order the room needs to reconcile with their predictions." Curious-student nuance (truthful one-sentence answer if asked, but intentionally outside this exercise's required scope): a function reading a global variable without reassigning it genuinely can see the global value directly — it's specifically assignment inside a function that creates a new local variable instead of modifying the global one.
