Learning objectives

By the end of this 75-minute session, students should be able to:

  • Create a dictionary with named fields, and access, add, update, and delete fields using key syntax.
  • Explain the difference between .get() (safe, with a default) and bracket notation (KeyError if missing) for dictionary lookups, and know when to use each.
  • Iterate over a dictionary's key/value pairs with .items().
  • Use a dictionary as a lookup table — mapping a category (like a tier name) to a value (like a discount rate).
  • Build a summary dictionary from a list of records, accumulating values by key with .get(key, 0) inside a loop.

One Customer

Teaching goal: dictionary literal syntax — curly braces, key: value pairs — and accessing a field by name with bracket notation. Say to the class (verbatim): "Curly braces this time, not square brackets. Each field gets a name — a 'key' — and a value, separated by a colon."

Live-code — Exercise 1

# --- Exercise 1 --- customer = { "name": "Alice", "email": "alice@example.com", "tier": "gold", "ytd_spend": 1200, } print(customer["name"]) print(customer["email"]) print(customer["tier"]) print(customer["ytd_spend"]) print(customer)

Curly braces {...} create a dictionary; each entry is a "key": value pair. The multi-line style with the trailing comma is just readability — it could be one line and mean the same thing. customer["name"] is bracket notation with a string key: "what's stored under the key 'name'?", not "what's at position 0?". print(customer) shows every pair in insertion order.

Line-by-line: - {"name": "Alice", "email": "alice@example.com", ...} — curly braces {...} create a dictionary; each entry is a "key": value pair, separated by commas, exactly parallel to a list's comma-separated items — but here, each value has a name attached to it rather than just a position. The multi-line style with a trailing comma after the last entry is just for readability; the whole thing could be written on one line and mean exactly the same thing. - customer["name"] — bracket notation, but with a string key instead of a numeric index — say explicitly, contrasting with Module 10: inventory[0] asked "what's at position 0?"; customer["name"] asks "what's stored under the key 'name'?" — a fundamentally different kind of question, even though the bracket syntax looks similar. - print(customer) — printing the whole dictionary shows all key/value pairs together, in curly-brace notation, in the order they were originally added — dictionaries in modern Python (3.7+) preserve insertion order, which wasn't always guaranteed in much older Python; a good "why does the order look predictable" answer if asked. Common mistakes: using = instead of : inside the dictionary literal — a SyntaxError; side-by-side customer["name"] = "Alice" (valid — how you update a field, Exercise 2) vs. {"name" = "Alice"} (invalid inside a literal). Forgetting quotes around a key (customer[name]) — Python treats name as a variable and raises NameError if none exists — another instance of "unquoted text is a variable reference, not a string" from Module 01. Check for understanding (guide, verbatim parenthetical): "What would customer["Name"] (capital N) return? (A KeyError — dictionary keys are case-sensitive strings, exactly like any other string comparison in Python; "Name" and "name" are different keys entirely, even though they look almost identical to a human reader.)"

Update and Add

Teaching goal: add a new field, update an existing one, and delete one with del — three distinct operations, all using the same bracket-notation syntax students already know from Exercise 1. Say to the class (verbatim): "Three changes to the same dictionary — adding a field that wasn't there before, changing one that was, and deleting one entirely. Print after each so you can watch it evolve."

The idea — the same one line means "add" or "update"

Say this symmetry explicitly

customer["phone"] = "555-1234" — assigning to a key that doesn't yet exist adds it. customer["tier"] = "platinum" — assigning to a key that does exist overwrites it. Identical syntax; Python decides which happens based only on whether the key was already present.

del customer["email"] — del is a keyword (not a method), and it operates on the access expression customer["email"]. It genuinely removes the key — a later lookup raises KeyError, unlike setting the field to None, which would leave the key present.

This card condenses the guide's line-by-line for Exercise 2. The add-vs-update symmetry is worth naming: there's nothing in the syntax itself that distinguishes the two operations. Contrast del (removes the key entirely) with customer["email"] = None (key stays, value is empty-ish) — a meaningfully different state that Exercise 3 explores.

Live-code — Exercise 2

# --- Exercise 2 --- customer = { "name": "Alice", "email": "alice@example.com", "tier": "gold", "ytd_spend": 1200, } customer["phone"] = "555-1234" print(customer) customer["tier"] = "platinum" print(customer) del customer["email"] print(customer)

Print after each step and watch the dictionary evolve: ["phone"] = ... adds a key that wasn't there; ["tier"] = ... overwrites a key that was; del customer["email"] removes a key (and its value) entirely.

Line-by-line: - customer["phone"] = "555-1234" — assigning to a key that doesn't yet exist adds it as a new field — there's no separate "add" syntax; adding and updating use identical syntax, and Python decides which happens based on whether the key was already present. - customer["tier"] = "platinum" — assigning to a key that does already exist overwrites its value — same syntax as the line above, different outcome, purely because "tier" was already a key and "phone" wasn't. - del customer["email"] — del removes a key (and its value) entirely. Contrast with setting a field to an empty string or None: del genuinely removes the key, so a subsequent customer["email"] lookup raises KeyError, exactly like the key was never there. Common mistakes: customer.delete("email") (a guessed method name) instead of the del keyword — del is a keyword, not a dictionary method, and operates on the access expression, not by being called on the dictionary. Attempting to del a key that doesn't exist — raises KeyError, same error family as looking up a missing key. Exercise 3 · 9 min · 0:18–0:27

Safe Lookup

Teaching goal: the most important distinction in this lab — .get() (returns a default instead of crashing) versus bracket notation (KeyError if the key is missing) — and when a professional would choose each. Say to the class (verbatim): "You just deleted email from this dictionary. What happens if code elsewhere in a larger program tries to look it up, not knowing it was deleted? Two different ways to ask, with two very different outcomes."

The idea — the decision rule

State this explicitly — it's the exercise's real point

Use .get() with a sensible default when a missing key is a normal, expected possibility your code should handle gracefully (a customer who genuinely has no phone number on file).

Use bracket notation — and let a missing key raise a loud KeyError — when a missing key would indicate a genuine bug or data-integrity problem you want to know about immediately, rather than silently paper over with a default.

The guide calls this "the exercise's real point". .get("email", "no email on file") takes the key plus a default to return if the key isn't present — since "email" was deleted in Exercise 2, it returns the default string, no error at all. Bracket notation on the same missing key raises KeyError: 'email'. Common over-correction: using .get() everywhere out of an instinct to "always be safe" — if customer["name"] were somehow missing, silently defaulting to "Unknown" might hide a real data problem a KeyError would have caught during testing.

Deliberately broken — bracket notation, no safety net

"email" was deleted back in Exercise 2. Bracket notation on a key that genuinely doesn't exist raises KeyError: 'email' and the program stops right here. The fixed version on the next slide wraps this in try/except and also shows the .get() alternative.

Line-by-line: customer["email"] — bracket notation, same as every prior exercise — but the key genuinely doesn't exist, so it raises KeyError: 'email'. Nothing prints; the program halts. Common mistakes: this is the mistake being demonstrated — reaching for bracket notation on a key that might not be there, with nothing to catch the fall.

Live-code — Exercise 3 (the professional handling)

# --- Exercise 3 --- customer = { "name": "Alice", "tier": "platinum", "ytd_spend": 1200, "phone": "555-1234", } print(customer.get("email", "no email on file")) try: print(customer["email"]) except KeyError as e: print(f"KeyError caught: {e}")

.get("email", "no email on file") returns the default — no error, program keeps running smoothly. The bracket-notation lookup still raises KeyError, but it's wrapped in try/except (Module 10 Exercise 5's pattern) so the program doesn't crash outright.

Line-by-line: - customer.get("email", "no email on file") — .get() is a dictionary method that takes the key you want, plus a default value to return if that key isn't present. Since "email" was deleted in Exercise 2, this returns the default string instead of raising any error — an explicit, readable fallback. - customer["email"] — bracket notation, same as every prior exercise — but the key genuinely doesn't exist, so it raises KeyError: 'email', wrapped here in a try/except so the program doesn't crash. - The decision rule to state explicitly: use .get() with a sensible default when a missing key is a normal, expected possibility to handle gracefully; use bracket notation — and let a missing key raise a loud KeyError — when a missing key would indicate a genuine bug or data-integrity problem you want to know about immediately. Common mistakes: forgetting the second argument to .get() (just customer.get("email")) — doesn't error; silently returns None. None is a real, distinct value, not "nothing happened". Iterate

Teaching goal: loop over a dictionary's contents with .items(), and understand what iterating without .items() gives you instead — keys only. Say to the class (verbatim): "Looping over a dictionary needs one new piece of syntax: .items(), to get both the key and the value together on each pass."

Live-code — Exercise 4

# --- Exercise 4 --- customer = { "name": "Alice", "tier": "platinum", "ytd_spend": 1200, "phone": "555-1234", } for key, value in customer.items(): print(f"{key}: {value}") print("--- without .items() ---") for key in customer: print(key)

.items() gives each key/value pair together, and for key, value in ... unpacks each pair into two loop variables — the same unpacking idea as Module 07's for price, tier in orders:. Looping over a dictionary directly (no .items()) gives only the keys, one per pass — not the values, not pairs.

Line-by-line: - for key, value in customer.items(): — .items() gives back each key/value pair together, and for key, value in ... unpacks each pair into two loop variables in one step — the same unpacking idea as Module 07 Exercise 4's for price, tier in orders: over a list of tuples (a dictionary's .items() behaves like a list of key/value tuples for looping purposes). - f"{key}: {value}" — produces the "name: Alice"-style formatted line the exercise asks for, ordinary f-string substitution. - for key in customer: (no .items()) — looping over a dictionary directly gives you only the keys, one per pass — not the values, not pairs. Easy to assume a bare for x in some_dict: would give values or pairs; it only ever gives keys. Have students write the required explanatory comment (the exercise's deliverable): iterating without .items() gives keys only; with .items() gives both keys and values together. Common mistakes: for key, value in customer: (forgetting .items() but still unpacking two variables) — raises ValueError: too many values to unpack (expected 2), since a bare dictionary iteration yields single keys, not pairs. Assuming the printed key order is alphabetical — it's insertion order; sorted() is a separate, deliberate step (Exercise 8). Check for understanding (guide, verbatim parenthetical): "If I wanted keys sorted alphabetically instead of in insertion order, what one built-in function from Module 10's Stretch challenge could help? Lookup Table

Teaching goal: use a dictionary as a lookup table — mapping a small, fixed set of categories (tier names) to associated values (discount rates) — a genuinely different use of a dictionary than Exercises 1–4's single-customer record. Say to the class (verbatim): "New use for a dictionary: not a record about one thing, but a lookup table mapping a category name to a value — tier name to discount rate. This is one of the most common, useful dictionary patterns in real business code."

The idea — one record vs. a rule for everyone

Two dictionaries, two different jobs

customer describes one person (Alice). tier_discounts is a general-purpose mapping — a rule that applies to every customer, usable to look up anyone's discount rate given their tier name.

tier_discounts.get(customer["tier"], 0) reads inside-out: customer["tier"] gets this customer's tier string; tier_discounts.get(..., 0) uses that string as the key into the lookup table, with a default of 0 so an unrecognized tier means "no discount" instead of a crash.

The default of 0 is a deliberate safety net — a typo or a new tier not yet added to tier_discounts returns 0 rather than crashing. Connect to Exercise 3's decision rule: an unrecognized tier is exactly the "expected possibility, handle it gracefully" case .get() is suited for. Note the single quotes around tier inside the double-quoted f-string — Python requires inner and outer quote characters to differ.

Live-code — Exercise 5

The idea — which dictionary am I inside right now?

Point at the nesting on screen

The outer dictionary's keys are product names; its values are themselves dictionaries, each with their own price/stock keys. The }} at the end of each entry: one closes the inner price/stock dictionary, the other (eventually) closes the outer one.

Sales by Region

Teaching goal: the most sophisticated pattern in this lab — build a summary dictionary from a list of transaction records, accumulating totals by key, using .get(key, 0) as the accumulator's safe starting point. A direct, real preview of what a GROUP BY does in SQL or a pivot table does in Excel. Say to the class (verbatim): "Last pattern of the day, and it's the one you'll use constantly in real analytics work: given a list of transactions, each tagged with a region, build a summary — one total per region — with a loop. This is exactly what a pivot table or a SQL GROUP BY does under the hood."

The idea — the single most important line in the lab

Walk it slowly, right to left

summary[region] = summary.get(region, 0) + t["amount"]

summary.get(region, 0) reads the running total so far for this region — default 0 because on a region's first appearance it isn't in summary yet, and without the default this would raise KeyError. + t["amount"] adds this transaction. summary[region] = ... stores the new total back — plain bracket assignment, no default needed, because assignment always works whether or not the key existed (Exercise 2's lesson).

Trace it by hand with the class, transaction by transaction: South/300 — summary.get("South", 0) is 0, so summary["South"] = 300. North/150 — summary.get("North", 0) is 0, so summary["North"] = 150. South/200 again — summary.get("South", 0) is now 300, so summary["South"] = 500. summary = {} is the accumulator-pattern skeleton from Module 06, but the "empty" starting value is now an empty dictionary, not 0 or []. for region in sorted(summary): sorts and returns the keys alphabetically.
