Learning objectives

By the end of this 75-minute session, students should be able to:

  • Navigate the file system entirely from the terminal — pwd, ls, mkdir, cd — without touching a mouse.
  • Explain the difference between the current working directory and the filesystem overall, and predict what pwd will print after a cd command.
  • Write, save, and run a .py file from the terminal with python3 filename.py.
  • Read a Python traceback (SyntaxError or NameError) and extract the line number and error type from it, rather than treating it as unreadable noise.
  • Explain why running a script depends on your current directory, and correctly use a relative path (python3 module02/hello.py) to run a script from a different location.
The verbs are taken verbatim from the guide's Learning Objectives. Objective 4 (reading a traceback) is the spine of Exercise 6 — the guide calls that "the most important exercise in this lab." Objective 5 (current directory determines what a script can find) is Exercise 7, which resolves confusion that may have already surfaced back in Exercise 3.

Terminal Warm-Up

Teaching goal: four foundational commands (pwd, ls, mkdir, cd) that every later exercise depends on — students need these to be reflexive, not looked-up, by the end of this block. Say to the class (verbatim): "Four commands. pwd tells you where you are. ls tells you what's here. mkdir makes a new folder. cd moves you into one. That's the whole toolkit for today's navigation." Live-code it one command at a time, narrating the output each time.

Keep this visible if teaching a mixed room. Do not assume Windows students will silently translate pwd on their own — name the equivalents up front. Live-code — Exercise 1

cd ~ pwd ls mkdir ism2411 cd ism2411 pwd

A terminal opens in your home folder — the opening cd ~ just makes that starting point explicit; in class you are already there. The seeded home folder here shows Desktop Documents Downloads; your real machine will list more. mkdir and cd print nothing on success — "no news is good news."

Line by line: - pwd — "print working directory": the full absolute path of where your terminal currently is. The single most useful debugging command in this whole lab — when anything goes wrong later, pwd is the first thing to run. - ls — lists the contents of the current directory. On Windows PowerShell also ls (aliased) or natively dir. - mkdir ism2411 — creates a new directory named ism2411 inside the current directory. No output on success — this trips up beginners who expect confirmation; say "no news is good news" and follow with ls for visual proof if you like. - cd ism2411 — moves your terminal's current location into the folder you just created. Also no output on success. - pwd (second time) — confirms the move; the printed path now ends in /ism2411 (or \ism2411 on Windows). Verified against ism2411/assets/lab-shell.mjs: /Users/student / Desktop Documents Downloads / /Users/student/ism2411. The guide writes the final path as /Users/yourname/ism2411 — the username is illustrative.

Common student mistakes

Watch for

Running mkdir ism2411 a second time by accident (e.g. after already cd-ing into it) — this either errors (File exists) or, depending on OS, creates a nested ism2411/ism2411/ folder. If you spot a student inside a doubly-nested folder, have them run pwd and read the output out loud themselves to spot the problem.

Typing CD or PWD in all caps out of habit — commands are case-sensitive on Mac/Linux terminals (Windows is more forgiving here).

Confusing mkdir (make a folder) with actually entering it — a student runs mkdir ism2411 then immediately tries the next exercise's commands, forgetting they're still in the parent. Watch for this specifically; it cascades into confusion for the rest of the lab.

The nested-ism2411/ism2411/ case is the memorable one — make the student read their own pwd aloud rather than pointing it out first.

The idea — print() is how a script speaks

Concept

print("Hello, ISM2411!") — print() is a built-in function; whatever's inside the parentheses (here, a string in quotes) gets written to the terminal.

This is the first time this semester it's said explicitly: print() is how a Python script produces visible output. A script with no print() calls can run successfully and show nothing at all — which surprises beginners.

python3 hello.py starts the interpreter and hands it your file to execute, top to bottom.

Don't rabbit-hole on "function" — the working definition today is "print() puts text on screen." The save step is the load-bearing habit: the terminal runs the file on disk, not the editor buffer.

Exercise 6 · 10 min · 0:40–0:50

Deliberate Error Experiment

Teaching goal: the most important exercise in this lab. Reading a traceback carefully — line number, error type, and message — is a skill every single future lab depends on, and this is the first dedicated practice at it. Say to the class (verbatim): "You're about to deliberately break your own code and read the error message on purpose. This is not a distraction from real programming — reading error messages is real programming. Every professional developer spends a large fraction of their time doing exactly this." Do, live, using the Exercise 3 hello.py: first introduce a typo (print → primt) and run; then the second type of error (remove a closing parenthesis) and run; then fix both and confirm hello.py runs cleanly again — do not skip that last step, ending on a broken file undermines the exercise's confidence-building purpose. Explain the difference between the two error types explicitly (verbatim): "NameError means Python understood the structure of your code just fine, but couldn't find something you referred to by name — like calling someone's name in a room and nobody answering. SyntaxError means Python couldn't even understand the grammar of what you wrote — like an incomplete sentence. Different category of problem, different place to look for the fix: a NameError means check spelling and definitions; a SyntaxError means check punctuation — matching quotes, parentheses, colons." Every student writes down, for each error: (a) the line number reported, (b) the error type, (c) one sentence on what the message tells them. That written analysis is the graded deliverable for this exercise, not just watching the demo.

The idea — read a traceback from the bottom up

Concept

Bottom line — the error itself: the error type (NameError, SyntaxError) and a message explaining what's wrong. Python 3.10+ often appends a helpful guess (Did you mean: 'print'?) — read all the way to the end.

The line just above, with the ^^^^^ marker: shows exactly which part of the line Python choked on.

File "hello.py", line 1, in <module>: tells you where — this file, this line number. Trivial for one line; the fastest way to find the problem in a 40-line script.

The first line — Traceback (most recent call last): — is boilerplate. It never contains the actual problem.

Beginners read top to bottom and get lost in the preamble. State the bottom-up order explicitly. The Did you mean hint is a real, useful feature, not a fluke.
